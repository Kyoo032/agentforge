# Chat

Chat is the default assistant: model picker, composer, thinking toggle, usage chip, and its own sessions at `/chat`. Since 2026-09-17 the sessions live **in the left rail** under `mode-chat` (`rail-thread-list`: `new-chat-link`, 4 rows, and a `threads-see-all` toggle that expands the list in place). There is no session column any more — `/chat` is just the chat pane. Stub replies without a gateway key; a saved key uses the live Toko Token gateway. A turn is three layers: **Thinking** (collapsible), **tools** (one row per call), **output** (the answer only — never a copy of the prompt, never a `Stub reply` prefix).

## Sub-features

- `chat-open` shows the empty Chat home with composer, model picker, and the single-row composer toolbar (`composer-toolbar`: `composer-attach` as a 32px icon, `model-picker`, `reasoning-effort`, `composer-enhance`, `composer-send`). Header chips sit in `chat-header`.
- `chat-empty-state` (0.15.0) is three things inside `chat-empty`: the headline, `chat-key-status` (one status line, a Settings link while no key is connected, and `chat-whats-this` → `chat-whats-this-body`), and `chat-suggestions` — **four** `chat-suggestion` intent cards with `data-idea` `plan` / `summarise` / `rewrite` / `decide` (`apps/web/components/chat-launcher.tsx:23`, `:93-100`). A card **fills** `composer-text` with its prompt; it never sends. There is no checklist, no mode cards and no model strip. `chat-key-status` follows the gate, not the key: `status: "ok"` → `Model key connected`; `stub` / `needs_key` → `Connect a key to go live` (`apps/web/components/chat-key-status.tsx:52-58`). "Offline demo" was removed in 0.15.0.
- `chat-model-switch` — clicking `model-picker` opens `model-picker-panel`, a **portalled** (`document.body`, `fixed`) list placed above the composer. Every option must be clickable with the mouse, not only reachable by Ctrl/Cmd+K and arrows. Clicking one changes the trigger label, survives a reload (`agentforge-chat-model`), and the next send posts that id in the run body. The trigger must stay readable on a narrow pane — `model-picker` `clientWidth` ≥ ~110px down to a 640px window; below that the composer toolbar wraps (Attach/Enhance move to another row) and `composer-send` stays visible and clickable inside `composer`.
- `chat-usage` shows the Chat header chip (`chat-usage`), a link to `/usage`. It has three labels, all prefixed `Usage ·` (`Pemakaian ·` on `id`): `Usage · —` while loading and for **every** unusable state (no wallet payload, `needs_key`, `error`, fetch failure), `Usage · Unlimited`, or `Usage · <left>` with the remaining USD. There is no `No key saved` and no `Usage unavailable` copy here — those belong to `settings-gateway-status`. On an `error` wallet the reason is only in the `title` attribute (`apps/web/components/chat-usage-chip.tsx:41-66`).
- `chat-context` shows the Chat header context chip (`chat-context`): a ring plus a short label (`<N> left` or `<N> used`). Click opens `chat-context-breakdown` with Conversation, Attachments, Knowledge (Soul / Memories / Sources, including RAG `N chunks · rag` or `fts` when retrieve ran), and Free. The `used / window` (empty: `0 / window`) line lives **inside the breakdown**, not on the closed chip. Sources excludes the thread's own work card (`threadId` on the context call).
- `chat-ingest` — every completed assistant turn rewrites one `Chat` work card per thread in the Knowledge Base (latest user + assistant, capped). `/knowledge` shows a `Chat` row named after the thread. Retrieval for that thread skips it. See [knowledge-ingest.md](./knowledge-ingest.md).
- `chat-enhance` rewrites the composer draft via `composer-enhance` (`POST /api/v1/prompts/enhance`). Stub rewrites locally. `composer-enhance-revert` / `aria-pressed` restores the pre-enhance text. A second sparkle after an edit treats the box as a new seed. Cancel aborts and does not replace the box.
- `chat-thinking` shows `reasoning-effort` next to the model picker, labeled **Thinking** (`Off` / `Light` / `Normal` / `Deep` / `Extra` / `Max` / `Ultra`). Values stay `none` / `low` / `medium` / `high` / `xhigh` / `max` / `ultra`. Default `medium` (Normal). Switching models does **not** yank the picker — the host snaps silently per model+wire. `Off` skips thinking events unless the model forbids `none` (GPT-6 → Light on the wire). Reasoning models also carry a `model-thinking-badge` in the picker. There is **no** `chat-wire` control.
- `chat-send` puts the user prompt in the transcript and returns the send button to `Send`. **Enter** sends (`submitOnEnter`); Shift+Enter stays newline. Packaged window must do this, not only `:3000`.
- `chat-keep-alive` — switching Chat ↔ Documents (or any rail job mode) must not unmount the visited mode. Drafts and in-flight runs survive. `WorkModeKeepAlive` keeps visited modes mounted.
- `chat-fail-closed` — a gateway 400/403 (illegal `temperature`, no access, quota) surfaces on `chat-error` / `composer-error`. Running/Thinking must clear (`onFailed` sets `running` false). Do not hang.
- `chat-probe` — host still retries contacting the model up to 3 times internally. The UI stays `Thinking…` (`thinking-placeholder` inside `message-thinking`) and `Sending…` on `composer-send`. Probe copy (`Probing`, `1st try`) must not appear on the frontend. After 3 failed tries, `chat-error` / `composer-error` reads `Could not reach {model} after 3 tries`. Packaged window must do this, not only `:3000`.
- `chat-new` starts a blank session from rail `new-chat-link` (including when the rail is collapsed) without losing the previous thread in the list. The model picker keeps its current value (does not snap to the catalog default). There is no header `new-chat`.
- `chat-switch` reopens the first thread from the rail block (`rail-thread-list` → `thread-item`). The picker restores that thread's last model from localStorage. If the destination thread has no stored model (or the stored id left the catalog), the picker keeps its current value — never the catalog default. First Chat load uses last-used (`agentforge-chat-model`), then catalog default.
- `chat-rail` keeps `mode-chat` visible. On Default, Documents/Research/Images/Videos/Presentation are also visible. `mode-agents` count is 0.
- `chat-rail-sessions` — directly under `mode-chat` the expanded rail shows `rail-thread-list`: `new-chat-link` (`New chat`), then at most `RAIL_RECENT_THREADS` (4) newest `thread-item` rows each with a hover `thread-delete`, then `threads-see-all` **only** when more than 4 exist. `rail.groupJobs` (`Job modes` / `Mode kerja`, sentence case) sits below all of it. A collapsed rail keeps `new-chat-link` and hides the session rows. A failed `GET /api/v1/threads` or a refused `DELETE` renders `rail-thread-error` inside `rail-thread-list`, under `new-chat-link`; the previously loaded rows stay on screen. A blank rail is a different bug from an error line.
- `chat-threads-expand` — `threads-see-all` is a toggle button, not a link: pressed (`aria-expanded="true"`) it lists every thread the host returned (capped at 40) in the same `rail-thread-list` and reads `Show less`; pressed again it collapses back to 4. The state is component-local — a reload starts collapsed. There is **no** second column and no route that opens one.

## How to get to it (user POV)

- Open `http://127.0.0.1:3000/chat`.
- Choose `Chat` on the left rail (`mode-chat`).
- `/` redirects to the first visible mode (Chat on Default).
- `/agents/<uuid>` redirects to Chat (Build is parked).

## Driving it with the DPSBuddy harness

Preconditions:

- Doctor exits 0 against `http://127.0.0.1:3000`.
- You are proving Chat at `/chat`.
- Unique prompt text, e.g. `VERIFY chat <run-id>: What is 2 + 3?`.
- `runtime: "stub"` for a stub-proof send. If doctor says `ai`, say so and treat the reply as live.

- **Open Chat.** Go to `/chat`. `model-picker`, `composer`, `composer-dropzone`, `composer-toolbar`, `composer-attach`, `reasoning-effort` and `chat-empty` are visible. `composer-send-hint` has count **0** — 0.15.0 removed the duplicate "Type a message to start" hint; the placeholder `Ask anything, or drop a screenshot, clip, or text file` carries it, and the drop zone renders no text of its own. `model-picker` reads `Model:` plus the current name. `reasoning-effort` is one `<select>` with `aria-label="Thinking"` and value `medium`; its options read Off / Light / Normal / Deep / Extra / Max / Ultra (no visible "Thinking" word — it is the accessible name). `chat-wire` count is 0. `chat-empty` headline is `Work starts here.` `mode-chat` plus the other work modes are visible. `mode-agents` count is 0.
- **Intent cards.** `chat-suggestions` holds four `chat-suggestion` rows (`plan`, `summarise`, `rewrite`, `decide`; titles `Shape a plan` / `Summarise something` / `Rewrite for a reader` / `Think a decision through`). Click the first: `composer-text` reads `Turn these notes into a step-by-step plan:` followed by a blank line, the URL stays `/chat`, `message-output` count stays 0, and no thread is created. Clear the box before the send below. Driven 2026-09-23.
- **Key status.** Read `chat-key-status` and `GET /api/v1/settings` → `gateway.status` together. `ok` reads `Model key connected` with `chat-whats-this` beside it; anything that is not `ok` and not in grace reads `Connect a key to go live` with a Settings link. On a webdev process whose env pins `AGENTFORGE_RUNTIME=stub` the gate is `stub` even with a key saved, so the line says `Connect a key to go live` while sends are live — see [settings.md](./settings.md) Gotchas. `chat-whats-this-body` ends "You can also sign in with a one-time code." on every build (a finding for the Personal app, which has no sign-in).
- **Usage chip.** `chat-usage` is visible in the Chat header. On stub / no key it settles on `Usage · —` (`id`: `Pemakaian · —`) unless the host is enforcing a plan, in which case the pill names the plan and seats. Assert the settled label, not the em dash alone. There is no token-allowance meter.
- **Context chip.** `chat-context` is visible in the Chat header. Closed chip text includes `left` or `used` (not `0 / window`). Click it: `chat-context-breakdown` shows Conversation / Attachments / Knowledge / Free, and the `used / window` line (empty thread: `0 / <window>`). After messages exist, used tokens are greater than 0.
- **Enhance.** Fill `composer-text`. Click `composer-enhance`. The box is rewritten (stub: same language, no “Enhanced prompt:” preface). Click again (`composer-enhance-revert` or `aria-pressed`) to restore. Send stays disabled while enhance is busy.
- **Send (short).** Fill `composer-text` with the unique prompt. Press Enter (or click `composer-send`). Before tokens, `composer-send` reads `Sending…` and `message-thinking` shows `thinking-placeholder` `Thinking…` (not `Probing` / `1st try`). `message-list` contains that prompt (20s). Shift+Enter must not send. On stub with thinking on, `message-thinking` is present **and open while the turn is live**. Arithmetic like `What is 2 + 3?` shows `message-tools` (Calculator) and `message-output` text `2 + 3 = 5` — not the question, not `Stub reply`. Assistant `message-output` renders markdown (bold/lists/links/images); user bubbles stay plain. `composer-send` reads `Send` again (30s). After refresh, thinking + tool + output stay on the turn (they do not vanish).
- **Live send with no reasoning and no tools.** On a live model that emits no reasoning and calls no tool, `message-thinking` exists only while the turn is in flight (with `thinking-placeholder` `Thinking…`) and has count **0** once it lands — the disclosure keys on `thinking || tools`. Driven 2026-09-23 on `GPT 5.6 Luna`: during send `message-thinking` 1, after `message-output` 0, `message-tools` 0. That is the pass, not a lost block.
- **`message-tools` is inside `message-thinking`.** Since 2026-09-23 the tool rows live in the thinking disclosure, not above the answer (owner ruling: the machinery used to be shown before the prose). A closed `<details>` keeps its children in the DOM, so a **count** assertion on `message-tools` / `message-tool` still passes after the turn lands, but a **visibility** assertion fails — the block auto-collapses when the turn completes and the user can reopen it. Assert count, or open `message-thinking` first. This is the same contract as `finance-phase-strip`.
- **Longer task.** Same transcript layout if several tools fire (search, then calculator, then prose): stacked `message-tool` rows inside `message-thinking`, then `message-output`. Tool rows are summarised, not dumped — a past-sessions call reads `Past chats · none`, never raw JSON.
- **New session.** Click `new-chat-link`. `chat-empty` shows `Work starts here.` again (10s).
- **Second send.** Fill and send a second unique prompt. `message-list` and the rail `rail-thread-list` contain it.
- **Knowledge card.** Open `/knowledge`. One `knowledge-source-row` with type `Chat` exists for this thread (not one per turn), `Indexed`, and `knowledge-loop-count-Chat` shows `data-count` ≥ 1.
- **Switch.** Click the rail `thread-item` whose text is the first prompt. `message-list` contains the first prompt and its answer.
- **Full list.** With more than 4 sessions, `threads-see-all` is visible in the rail with `aria-expanded="false"`; click it. `rail-thread-list` now shows every session (up to 40) and the row reads `Show less` / `aria-expanded="true"`. Click again: back to 4 rows. No second column appears at any point.
- **Delete a session.** Hover a `thread-item` row and click its `thread-delete`. A native `window.confirm` fires — register the dialog handler *before* the click or the driver hangs. On `id` it reads `Hapus "<title>"? Tindakan ini tidak dapat dibatalkan.`. Accept: the row disappears, the list refills from the tail (still 4 rows while more than 4 remain), and `threads-see-all` disappears once 4 or fewer are left. Deleting the open thread also takes the URL back to `/chat`.
- **New chat from the rail with a thread open.** Open a thread that has at least one turn, then click `new-chat-link`. URL returns to `/chat` with no `?thread`, `message-output` count drops to 0, `chat-empty` returns, and no `thread-item` carries `aria-current`. Reopen the row: the turn is still there. The pane was cleared, not the thread.
- **Locale (id).** With the desk on `id` (see [locale.md](./locale.md)), Chat reads `Chat baru`, `Kerja dimulai di sini.`, composer placeholder `Tanyakan apa saja, atau lepas tangkapan layar, klip, atau berkas teks`, send button `Kirim`, `Chat baru` on the rail `new-chat-link`, and `Semua sesi` on `threads-see-all` once it shows (`Lebih sedikit` while expanded); the `rail-thread-list` group is labelled `Sesi chat terbaru`, the delete confirm reads `Hapus "<title>"? Tindakan ini tidak dapat dibatalkan.`, and the Thinking ladder reads `Berpikir Mati Ringan Normal Dalam Ekstra Maks Ultra`. Testids are locale-invariant.
- **IDE proof.** Screenshot under `evidence/chat/<run-id>/` showing thinking, a tool row, and output.
- **Cloud.** Same steps via `page.getByTestId` in `foundation.spec.ts` (do not run that spec on Windows).

## Gotchas

- The composer toolbar **wraps** (`flex flex-wrap items-end`); its left group must never go back to `overflow-hidden`. It used to clip, which hid the model palette (a thin sliver in the 32px toolbar row, clicks falling through to `message-list`) and squeezed the trigger to 18px on narrow panes. Any popover anchored in that group (model picker, and anything added next to it) **must** be portalled to the body and positioned with `placePickerPanel` (`apps/web/lib/picker-panel.ts`). Playwright still calls a clipped option "visible", so assert the click actually changes the trigger label — a visibility check alone will not catch it.
- The second column is gone for good (deleted 2026-09-17), so a 480px window leaves the chat pane ~248px (rail 232 only) whatever the session list is doing — expanding `threads-see-all` only makes the rail scroll, never narrower panes. It used to be ~48px because rail 232 + thread list 199 were both fixed with no responsive auto-collapse. Collapse the rail (`rail-collapse`) to judge the pane below 480px.
- `new-chat-link` is the only New chat control, in the left rail under Chat, including when the rail is collapsed. There is no header `new-chat`. The smoke clicks `new-chat-link`.
- `thread-item` / `thread-delete` now exist in exactly one place, `rail-thread-list`. `thread-list`, `thread-list-new-chat` and `thread-resize` no longer exist anywhere — a locator on them is a stale recipe, not a regression.
- The collapsed rail shows only 4 sessions. A thread that exists but is not in the rail is not a bug — press `threads-see-all` before calling a session lost.
- `thread-delete` is `opacity-0` until its row is hovered or focused (`apps/web/components/rail-recent-threads.tsx:78-80`), not `hidden`. Playwright calls it visible and clicks it regardless; a human must hover. Hover the parent row rather than forcing visibility.
- **Do not send immediately after clicking a `thread-item`.** The URL carries `?thread=<id>` before the pane has loaded that thread, and the composer creates a *new* thread when it fires inside that window — the message lands in the new session and the URL is rewritten to it. Wait for the transcript (or `chat-empty`) to settle first. Reproduced deterministically; see `docs/internal/unreleased.md`.
- A thread created by `POST /api/v1/threads` **without** a `title` never appears in `rail-thread-list`: the host filters every locale's default title (`New thread` / `Percakapan baru`) out of `GET /api/v1/threads` (`packages/host/src/handlers/threads.ts:29`, `packages/host/src/thread-title.ts:20-22`). Seed with a title. Conversely a seeded title is never overwritten by the first prompt (`packages/host/src/threads.ts:240`), so the row will not echo what you sent.
- Opening `/chat?thread=<id>` and sending **before** `GET /api/v1/threads/<id>` resolves must not fork a second thread. `ensureThread` (`apps/web/components/chat-session.tsx`) falls back to the URL's id (`pendingThreadRef`) while that GET is in flight, because `threadIdRef` only fills once it lands; `composer-send` stays enabled the whole time (Enter bypasses a disabled button anyway, so a gate would not have fixed it). Rail sessions make the race trivial to hit. Drive it by delaying only `GET /api/v1/threads/<id>` (a `page.route` predicate on `url.pathname`, never a `**/threads/<id>*` glob — that also swallows `/runs/text`) and assert `GET /api/v1/threads?scope=all` keeps the same count. Driven 2026-09-17: pre-fix 1 → 2 threads with the opened thread left at 0 messages.
- Wait for `composer-send` text `Send`, not a fixed sleep. Stub and live both hold the button in a busy state.
- Live contact miss (no channel, 502/503, network): host retries the same model up to 3 times internally. The UI stays `Sending…` / `Thinking…` — do not require `1st try` labels on the frontend. Then `chat-error` / `composer-error` reads `Could not reach {model} after 3 tries`. Do not treat that as a harness fail if the gateway is down.
- GPT-6 with Thinking **Off** snaps to **Light** on the wire (`none` is not allowed). The picker still says Off.
- Host auto-routes the POST path. Product Chat does not send `wire` (always auto). GPT-5 / GPT-6 / o-series → `/v1/responses`; Claude 5 / Opus 4.7 / 4.8 / Sonnet 4.6 → `/v1/messages` with the gateway key as `x-api-key` + `anthropic-version: 2023-06-01`; Gemini chat → `/v1beta/models/{id}:generateContent` (404 falls back to Completions); else `/v1/chat/completions`. Probe is still only `GET /v1/models`. Claude 5 never sends `thinking: { type: "enabled", budget_tokens }`. Off → `thinking: { type: "disabled" }`; thinking on → `thinking: { type: "adaptive" }` + `output_config.effort` after a silent closest snap (Ultra → `max` on Messages; Extra → `xhigh`; Max stays `max`). Toko Completions keeps Ultra as `ultra`. Official OpenAI Completions/Responses snap Ultra → `max` (never `xhigh`, never send `ultra`).
- A thinking **400** is a bad request for that send — not a signal to try another path. Fallback is 404-only to Completions.
- A 403 (`no access` / quota) must fail closed in seconds, not sit on Running until the 60s idle watchdog.
- `chat-usage` loads asynchronously from `/api/v1/settings`. Assert the settled label, not the initial `…`.
- Empty-state “paste a … key” uses ping `gatewayName` (Toko Token on webdev). Local flavor windows say AIHub — [desktop-brands.md](./desktop-brands.md).
- `chat-context` is a local estimate (~4 characters per token) from visible text and thinking, not the gateway tokenizer.
- Cursor's browser overlay can inject `data-cursor-ref` and eat clicks. Report it; do not retry by coordinates forever.
- Sending on `runtime: "ai"` spends the operator's gateway. Do not do that as a silent stub check.
- MiniMax M3 (`minimax-m3`) streams thinking in `reasoning_content`. That belongs in `message-thinking`, not in `message-output`.
- Arithmetic fires calculator. The **output** is `2 + 3 = 5`. The tool row stays visible after the run.
- Do not POST `/api/v1/chat` as a substitute for the composer.
- Documents / Research / Presentation collect `assistant.delta` only (JSON/markdown output). They ignore thinking events on purpose so drafts are not polluted with chain-of-thought.
- The Chat work card is written after the stream closes (fire-and-forget). If `/knowledge` does not show the row at once, reload once. A thread with only media output (no assistant text) writes no card.
- Remote media in an assistant reply no longer renders inline — it degrades **silently** to an ordinary link. `apps/web/lib/renderable-media.ts` treats only `/api/v1/media/`, `agentforge://media/`, and `data:image/{png,jpeg,webp,gif}` as renderable; `apps/web/lib/parse-markdown.ts` turns any other `![alt](url)` into a link whose text is the alt text, or the raw URL when there is no alt. There is no “image blocked” copy and no broken-image icon. Assert an `<a>` where an `<img>` used to be inside `message-output`; do not wait for an error that never comes.
- A rejected saved key fails the send with the **same** localized sentence in both `chat-error` and `composer-error`: `The gateway did not accept this API key (status_code=401). Check the key in Settings.` The status code stays in the headline and the copy follows the desk language (`packages/core/src/gateway-http-copy.ts`). A driver waiting only on `message-output` hangs to timeout — race `message-output` against `chat-error` and `composer-error`. Driven: a 180s wait on `message-output` timed out when the real outcome was a 401 in `chat-error` two seconds after send.
