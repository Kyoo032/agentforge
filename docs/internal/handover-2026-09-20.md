## Environment notes for cloud sessions

Read this before deciding a cloud session "cannot verify" something. Written 2026-09-20 from the Lane A session
(PR #60), which used the workaround below to run the full workspace test suite.

### `pnpm install` fails, and the workaround

`packages/core/package.json` resolves `xlsx` from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, not from
the npm registry. The agent container's network policy denies that host — `pnpm install --frozen-lockfile` dies
with `ERR_PNPM_FETCH_403` after downloading everything else. `registry.npmjs.org` itself is on the proxy's
no-proxy list and works fine, so the blockage is this one dependency.

To get a working `node_modules`, point that one dependency at the registry, install, then **put the manifests
back before committing**:

```bash
# from the repo root; keep the backups outside the repo
cp package.json pnpm-lock.yaml "$SCRATCH/"
cp packages/core/package.json "$SCRATCH/core-package.json"

# in packages/core/package.json, change the xlsx value
#   from  "https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz"
#   to    "0.18.5"
pnpm install --no-frozen-lockfile     # --no-frozen is required: a manifest changed

# ... run lint, tsc, pnpm test ...

cp "$SCRATCH/package.json" "$SCRATCH/pnpm-lock.yaml" .
cp "$SCRATCH/core-package.json" packages/core/package.json
git diff --name-only    # confirm neither pnpm-lock.yaml nor packages/core/package.json is listed
```

**The restore step is not bookkeeping.** `pnpm install` rewrites `pnpm-lock.yaml`. If that file reaches a commit
it pins the whole repository to `xlsx` 0.18.5 — a downgrade nobody reviewed, arriving through a lockfile nobody
reads. Check `git diff --name-only` before every commit in a session that used this.

**What the workaround proves and what it does not.** With it, `pnpm test` runs the whole workspace: on PR #60 that
was 7 of 8 packages green and `@agentforge/host` at 1707 passed, 2 failed. Both failures are pre-existing on
`main` and environmental, not signals about any branch: `edit/ffmpeg-binary.test.ts` asserts a Windows
`System32\where.exe` path, and `edit/import-ipc.test.ts` expects 201 and gets 400. `biome` and `tsc` need no
network at all once `node_modules` exists. What the suites then exercise is `xlsx` **0.18.5**, not the pinned
0.20.3, so nothing that touches the spreadsheet parser is actually validated — treat any xlsx-adjacent result
from a cloud session as unproven. Booting and driving the app was not attempted.

### Why the fix is an allowlist, not a dependency change

The obvious-looking fix — move `xlsx` to the npm registry permanently — is a security regression, and was
rejected on 2026-09-20 for that reason.

npm's `latest` for `xlsx` is **0.18.5**, published in 2022; the registry has no newer version, because SheetJS
stopped publishing to npm and moved to their own CDN. So the registry copy is not the same package from a
different host, it is roughly two years behind the pinned 0.20.3, and the releases in between are where the
publicly known `xlsx` advisories were fixed:

| Advisory | Affects | Fixed in |
|---|---|---|
| CVE-2023-30533 — prototype pollution | `xlsx` < 0.19.3 | 0.19.3 |
| CVE-2024-22363 — regular-expression denial of service | `xlsx` < 0.20.2 | 0.20.2 |

Both therefore apply to the registry's 0.18.5 and to neither the pinned 0.20.3. *(Version facts read off
`registry.npmjs.org` on 2026-09-20 by the Lane A session; the two advisory IDs and their ranges were confirmed
separately by the PR #60 verifier thread the same day. The GitHub advisory API is not reachable from the agent
container, so neither was re-read there.)*

That matters for this product specifically: this is code that parses user-uploaded spreadsheets, and Phase 3 is
the phase that makes the server multi-tenant. Shipping a known-vulnerable parser in front of other tenants'
uploads to make cloud installs convenient is the wrong trade.

Vendoring the 0.20.3 tarball into the repository was the other candidate and is also not possible from a cloud
session: the tarball itself is what the policy blocks, so no agent can fetch the bytes to vendor.

**What Kyo needs to do:** allowlist `cdn.sheetjs.com` in the environment's network policy. That fixes every cloud
session at once, changes no dependency, and retires the workaround above. Until then the workaround is the
standing procedure, with its caveat.

## PR #60 — fix(edit): close the cross-tenant discard IDOR, scope the edit store (Phase 3 lane A)

**Link:** https://github.com/Kyoo032/agentforge/pull/60 — merged to `main` as `b868d47` (merge commit), head
`769303a`. Twenty files: eight source files under `packages/host/src/edit/` and `handlers/edit.ts`, one new test
file, eight updated tests, three docs. No migration, no schema change, no `tenants` table, no change to
`getTenant`. Those belong to lanes B and C and the diff was checked for them.

### What changed and why

Before this PR, `POST /api/v1/edit/projects/:projectId/unplaced/:itemId/discard` resolved the caller's desk and
then threw the result away. It updated `edit_unplaced` by item id alone, ignoring both the desk and the
`:projectId` in its own path, and returned the updated row. Any desk that knew an item id could soft-delete
another desk's unplaced item and read its `prompt` text back in the response. The sibling `…/place` handler
already scoped through `foldProject`, so the discard route was the one that had been missed.

Around it, eight edit-store functions were safe only by convention: they took an id and either made the desk
optional or checked ownership in application code after an id-only read. The next handler that forgot a
`foldProject` would have opened the same hole elsewhere.

After this PR:

- The discard route calls `foldProject(projectId, tenant.workspaceId)` first and pins the row with
  `and(editUnplaced.id, editUnplaced.projectId)` in the update's `WHERE` (`packages/host/src/handlers/edit.ts:494-513`).
  A foreign desk gets a 404 that carries nothing from the other desk's row, and the row is untouched.
- The scope is a required argument that sits in the SQL `WHERE`, so a caller that forgets it does not compile:
  `loadProjectRow` and `foldProject` (`packages/host/src/edit/ops.ts:75-86`, `:129`), `appendOps` via a required
  `workspaceId` on `AppendOpsOptions` (`ops.ts:27-35`, load at `:172`, project update at `:275`), `getEditJob` and
  `patchJob` (`packages/host/src/edit/jobs.ts:96-132`), `cancelEditJob` (`jobs.ts:442`), `undoCard` and `keepCard`
  (`packages/host/src/edit/undo.ts:41-100`, card read and status update both pinned to the project).
- Carried along by the same argument: `renderParityFrame` loses its optional scope (`parity.ts:26`); the agent
  tool backend's `reviewGateOpen` and `cancelJob` scope through the run's own context (`backend.ts:102-111`,
  `:184-191`); every `edit_cards` status write in `jobs.ts`, `backend.ts` and `start-generate.ts` is pinned to
  its project.
- The background job runner has no request to scope by, so it uses two named unscoped reads,
  `workerWorkspaceId` (`ops.ts:97`) and `workerJob` (`jobs.ts:141`, module-private), and a test fails if
  `handlers/edit.ts` ever imports either one.

The boundary enforced is the desk (`workspaces.id`), which exists today. When lane B adds `tenant_id` above it,
a foreign tenant is already a foreign desk to the edit store, so nothing here needs revisiting.

### What changed and why

Before this PR the database had no notion of a tenant. `organizations` was the top of every scope, its `slug` was
globally unique (`0000_smiling_skin.sql:91`), and `TenantContext` carried an `organizationId` but nothing above it.

substituted home for a workspace id it did not recognise, `workspace-id.txt` named one desk for the whole machine,
and the CSRF token was bare randomness, so a token minted for one session was accepted from any other.

After this PR:

- `getTenant(input)` (`packages/host/src/tenant.ts:88`) takes either the bare desk id every existing call site
  already passes or the request itself. With a session it resolves from that session and nothing else
  (`resolveFromSession`, `:105` → `resolvePortalTenant`). With no session in server mode it throws

  preference. This is the one departure from the spec: the spec had `requireTenant` at the top of `dispatch`; the
  author chose the ambient store so lane C does not refuse every hosted request until lane E sweeps the call
  sites, and `getTenant(request)` remains the contract lane E sweeps to. `web-migration-plan.md` records this.
- `resolvePortalTenant` (`packages/db/src/portal-owner.ts:186`) only reads. Tenant row missing or not `active` →
  `tenant_inactive` 403; org not under the session's tenant (pinned in the same `WHERE`, `:201`) → `org_inactive`
  403; user not a member → `user_inactive` 403; a preferred desk the org does not own → `workspace_not_found` 404
  (`:218`, `:222`). `dispatch` attaches a cleared `agentforge_workspace` cookie to that one 404 code only
  (`router.ts:405`), so a handler's own "thread not found" never clears a desk selection.
- First sign-in provisions: `handleLogin` calls `deps.provision(...)` (`auth/routes.ts:248`) after the token
  exchange and before `store.create(session)` (`:258`), so a refused provisioning leaves no session row.

  memberships and a home desk, idempotently. An org already held under another tenant throws
  `PortalProvisionError` (`:113`) → `org_inactive` 403 (`routes.ts:94`); rows are never re-homed. The `@agentforge/db`
  import is dynamic (`auth/index.ts`) so the desktop never opens SQLite by importing the router.
- `workspace-id.txt` is desktop and webdev only: both accessors return early in server mode (`workspace.ts:24`,

- CSRF token is `<salt>.<HMAC(key, sessionId.salt)>` (`csrf.ts:87`), verified after the constant-time pair check
