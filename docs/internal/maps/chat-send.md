## Overview

One user turn in Chat: text in the composer, Enter, an assistant answer streaming into the transcript. The path crosses four layers — renderer, transport (HTTP or Electron IPC), host run orchestrator, core runtime — and everything the user sees between "Send" and the finished message is a server-sent-events stream of `RuntimeEvent`s.

The thing to hold onto: **the streamed text is not what ends up on screen.** The deltas paint a live bubble; when the run completes the renderer throws that state away and re-fetches the thread, so the persisted database copy is what the user actually keeps.

## How it works

### 1. Composer → request

`ChatComposer` (`apps/web/components/chat-composer.tsx`). Enter is handled by `submitOnEnter` (`apps/web/lib/composer-enter.ts:7-26`), which ignores Shift/Alt/Ctrl/Meta and IME composition (`keyCode === 229`); the Send button submits the same `<form>`. `send()` (`apps/web/components/chat-composer.tsx:306`) classifies attachments, ensures a thread exists (`POST /api/v1/threads`), optimistically appends the user's own message to local state (`apps/web/components/chat-session.tsx:490-492`), then POSTs:

```
POST /api/v1/threads/:threadId/runs/text
{ content, model, thinking, reasoningEffort }
```

(`apps/web/components/chat-composer.tsx:400-411`; `/runs/image` and `/runs/video` are the media variants at `:467`.)

### 2. Transport — one function, two worlds

`apiFetch` (`apps/web/lib/api-client.ts:393`) is the only place that knows whether this is webdev or the packaged app: it picks the request's path and hands the transport to `transportFetch` (`:170`). Since 2026-09-29 it also shares plain GETs that are in flight together: a GET with no option but its method, less than 2 s old, joins the request already on the wire and gets its own `response.clone()` (the last joiner takes the original), and the entry is dropped when it settles (`sharedRead`, `:316`). Any write clears every entry when it starts and again when it is over (`dropSharedReads`, `:293`), and a streamed write, which is what a chat run is, when its body has been read to the end, has failed, or has been cancelled (a job stream is read only to its terminal event and then cancelled, which a `TransformStream` `flush` would miss; `sendWrite`, `clearReadsWhenStreamEnds`, both in `apps/web/lib/api-client.ts`), so the refresh after a run cannot join a read that began mid-stream. An event stream is never shared. Boot went from 19 GETs to 13 on a cold `/chat`. `apiFetch` itself is not a cache: a read that starts after another settled asks again. **One route is the exception, and only for the callers that opt in** (2026-09-29): `GET /api/v1/settings` was read four times on a cold `/chat` (the shell's gate, the key pill, the usage chip, the composer's needs-key hook), one after another, so nothing above could fold them, and each was 274 KB. The shell's gate read (`readSettings({ fresh: true })`, `apps/web/src/App.tsx:224`) now leaves its answer for the readers that only display it (`chat-key-status.tsx`, `chat-usage-chip.tsx`, `use-desk-needs-key.ts`, `use-job-model.ts`) through `readSettings` (`apps/web/lib/settings-read.ts`): one request and one parse, at most 2 s old, dropped by every write through `subscribeToWrites` (`api-client.ts:286`), never keeping a refusal. Measured in headless Chromium on the dev desk: 12 requests and 1 161 641 bytes before, 9 and 337 853 after (4 settings reads to 1, the payload itself unchanged until the host is restarted onto the slimmer answer). Map: [`shell-rail-and-workspaces.md`](shell-rail-and-workspaces.md) § 8.

- **Web:** plain `fetch`, stamped by `withMutatingHeaders` (`apps/web/lib/api-client.ts:153-165`) on mutating methods only: `x-agentforge-transport: web`, and alongside it the double-submit CSRF token in `x-agentforge-csrf` when one is available. The CSRF half is a hosted-mode rule and is mapped in [`hosted-server-mode.md`](hosted-server-mode.md), not here.
- **Packaged:** `invokeDesktop` → `window.agentforge.invoke` → `ipcRenderer.invoke("host:request", …)` (`apps/desktop/preload.cjs:25`). A `{type:"stream"}` result is rebuilt into a real `ReadableStream` fed by `host:stream-chunk` / `host:stream-end` / `host:stream-error` (`apps/desktop/preload.cjs:27-56`), and abort goes back out over `host:stream-abort` (`apps/web/lib/ipc-abort.ts:18-28`).

Either way `apiFetch` hands back a `Response` with `Content-Type: text/event-stream`, so `readSse` never learns which transport ran.

### 3. Host — gate, then run

`packages/host/src/router.ts:255-257` maps the route to `handleRun` (`packages/host/src/handlers/runs.ts:27`). First thing it does, before touching the database or the gateway: `requireGatewayAllowedFor(tenant)` (`packages/host/src/handlers/runs.ts:31`). A closed gate throws `GatewayBlockedError` and the request answers a flat `403 { error: "gateway_blocked", status, message }` (`packages/host/src/errors.ts:20-25`) with no SSE stream at all. See [`settings-and-gateway-gate.md`](settings-and-gateway-gate.md).

Otherwise `startModalityRun` (`packages/host/src/runs.ts:125`) runs the turn:

1. Parse and validate the body (`parseTextRunInput`, `packages/core/src/content/parse-run-input.ts:114`) — empty content or an `image_url` part on the text route is a 400.
2. Redact attachments unless `injectionGuardBypass`; load the thread (404 if missing); resolve the model; build the knowledge injection and the final system prompt.
3. Push `": connected\n\n"` onto an async queue immediately so headers flush.
4. **Arm the run-stall guard** (`packages/host/src/runs.ts:195`, `packages/host/src/run-stall.ts`).
5. Kick off the background `work` IIFE: persist the user message, set the thread title, `insertRun` (status `streaming`), load history, `createRuntime(settings)`, emit `run.started`, then `runtime.execute({...})` inside `withRunContext`.
6. The generator yields whatever `send()` pushed (`packages/host/src/runs.ts:450-456`). Each frame is `encodeSse(event)` — `event: <type>\ndata: <json>\n\n` (`packages/core/src/sse.ts:6`).

`work` is deliberately **not** awaited by the generator's `finally`: a wedged model call must not block `host:stream-end`.

### 4. Runtime — probe, stream, coerce

`AiSdkRuntime.execute` (`packages/core/src/runtime/ai-sdk-runtime.ts`) builds the wire body, resolves effort, and enters the contact loop: up to `MODEL_CONTACT_ATTEMPTS = 3` (`packages/core/src/runtime/retry.ts:4`), each retry emitting a fresh `run.probing` frame (`packages/core/src/runtime/ai-sdk-runtime.ts:443`). A non-OK upstream response is read through `readHttpErrorBody` under a 2 s cap (`GATEWAY_ERROR_BODY_MS`, `packages/core/src/models/request-constraints.ts:123`) and turned into a `gatewayFailure`; `isRetryableModelFailure` (`packages/core/src/runtime/retry.ts:59-81`) decides whether to try again — with one carve-out, the "no first token / no stream events" wording is a hard stop, never retried (`:76-79`).

Reasoning effort has **two unrelated mechanisms** that both land as `reasoning_effort` on the wire:

- **Chat's own Thinking picker.** `readOptionalReasoningEffort` (`packages/core/src/models/reasoning-effort.ts:67`) defaults to `medium`, coerces to `none` when `thinking: false`, and accepts the UI aliases. The runtime then calls `snapReasoningEffort` (`packages/core/src/runtime/effort-allowlist.ts:74-81`), which picks the per-model, per-wire allowlist and snaps through `closestReasoningEffort` (ties go cheaper; `none` is never upgraded when `none` is itself allowed). `GPT_6_EFFORTS` (`packages/core/src/runtime/effort-allowlist.ts:18`) simply omits `none`, which is how a GPT-6 request that asked for Off comes out as `low`. Finally `applyReasoningEffortToChatBody` writes `reasoning_effort` onto chat-completions bodies only (`packages/core/src/models/reasoning-effort.ts:156-162`); Anthropic Messages and Gemini `generateContent` get their own shapes from `packages/core/src/runtime/chat-wire.ts:189-252`.
- **The job knob, which Chat never uses.** `applyJobThinking` (`packages/core/src/models/job-thinking.ts:49-58`) forces `reasoning_effort: "low"` on always-thinking families, but only when `input.jobMode` is set (`packages/core/src/runtime/ai-sdk-runtime.ts:274-277`). `packages/host/src/runs.ts:286-296` builds the `runtime.execute` options with **no `jobMode` key at all** — grep `runs.ts` for `jobMode` and you get nothing. The contract says so out loud: "Chat leaves this unset and keeps its own Thinking control" (`packages/core/src/runtime/types.ts:54-58`).

### 5. The watchdogs — there are three

One rule, `streamWatchdogDeadline` (`packages/core/src/runtime/stream-watchdog.ts:88-97`), used by three separate instances:

| Instance | Scope | On fire |
|---|---|---|
| `AiSdkRuntime.consume` (`packages/core/src/runtime/ai-sdk-runtime.ts:603`) | one gateway call | aborts that call; the probe loop may retry it |
| `armRunStallGuard` (`packages/host/src/run-stall.ts`, armed at `packages/host/src/runs.ts:195`) | the whole SSE run | `run.failed` + `run.completed`, stream closed, run marked failed — never retried |
| `apps/web/components/chat-composer.tsx:382` | the browser tab | aborts the fetch, shows the localised abort sentence (`:494`) |

Budgets (`packages/core/src/runtime/stream-watchdog.ts`): `STREAM_TTFB_MS = 120_000` / `STREAM_IDLE_MS = 60_000` for ordinary models; `STREAM_REASONING_TTFB_MS = 240_000` / `STREAM_REASONING_IDLE_MS = 180_000` for reasoning models. `isWatchdogReasoningModel` (`:43-49`) covers the Claude 4/5 families plus `QUIET_REASONING_FAMILY` — `^(deepseek-v4|glm-5\.3|kimi-k3|qwen3\.8-max)` (`:40`).

**Quiet reasoning is the whole point of that second pair.** Until the model produces real output the first-token budget governs and it is a **hard, non-rearming cap**: a frame carrying no output (the AI SDK's `step-start`, a keep-alive) must not push it out, or a gateway that heartbeats forever without answering would hold a run open forever (comment at `:82-86`). Only `touchOutput()` flips `streaming` true and hands over to the idle budget. The quiet families get the long budgets because their `reasoning_content` is dropped by AI SDK 4 before it reaches `onEvent`, so a thinking model looks dead on the wire. A per-run `streamWatchdog` override can only **raise** these floors (`raisedLimit`, `:59-66`); Chat passes none, job routes do.

### 6. SSE → screen

`readRunStream` (`apps/web/components/chat-composer.tsx:131-173`) reads the body, feeds `consumeSse` (`apps/web/lib/sse-client.ts:14-33`), and dispatches: `run.started` / `run.probing` → `onStarted`; `assistant.delta` → accumulate `streaming`; `assistant.thinking` → accumulate `thinking`; `tool.started` / `tool.completed` → the tool list; `run.failed` → `onFailed` + `composer-error`. A refused HTTP response takes the same path through `fail` (`:319-325`, called at `:413` and `:480`). `ChatSession`'s `onFailed` (`chat-session.tsx:508-511`) clears `running` and sets `sendFailed` so the live mascot goes to `error`. It does not copy the sentence into `chat-error`. That banner is for a pane that could not open.

While anything is live, or a send just failed, `ChatTurn` renders inside a `data-testid="assistant-live"` wrapper (`apps/web/components/chat-session.tsx:436`): `NultronMascot` sits beside the turn (`apps/web/components/chat-turn.tsx:86`) as a 40 px head (the MINI rig), with `busy` set while `live.running`. Its state is `liveTurnMascot` (`apps/web/lib/mascot-triggers.ts:72`): `error` when `sendFailed` is set; `lets-go` for the first 900 ms (`LETS_GO_MS`) of a new chat's first turn, held by `useHoldOnMount` (`chat-turn.tsx:51`) from `firstTurn`, which is true while the thread has no assistant message (`chat-session.tsx:446`); then `thinking` until answer text arrives, then `answering`. `data-busy` appears only in `thinking` and `answering`, because `lets-go` and `error` are one-shot states. The thinking `<details>` shows `thinking-placeholder` until the first thinking token (`apps/web/components/chat-turn.tsx:111`), tools render as `message-tools` (`apps/web/components/chat-turn.tsx:118`), and the answer renders through `FormattedText` as `message-output` (`apps/web/components/chat-turn.tsx:136`). A paragraph that is only a link, a file URL, or a host image becomes a card in `presentStandaloneLink` (`apps/web/components/formatted-text.tsx:63`). A markdown image whose source must not auto-load (`![alt](https://…)`) is an image card with no `<img>` (`formatted-text.tsx:54`), marked `fromImage` on the link (`apps/web/lib/parse-markdown.ts`). Search hits and a titled tool payload become job cards under the answer (`apps/web/components/chat-turn.tsx:146`). On `onComplete` the live stream state is cleared and `refreshMessages` does a `GET /api/v1/threads/:id` (`apps/web/components/chat-session.tsx:528`), after which the same text re-renders from the persisted message — through a different component, with the same `message-output` testid (`apps/web/components/chat-turn.tsx:220`, `:255`). A failed send keeps the error mascot up (`sendFailed`) until the next send or a thread switch. The empty desk shows the same character, whole body, in the hero: `ChatHero` mounts `NultronMascot` with `variant="full" tight` (`apps/web/components/chat-hero.tsx:70`), and `ChatLauncher` mounts the hero (`apps/web/components/chat-launcher.tsx:96`); see § 9. States, sizes and renderers are [`mascot-and-brand.md`](mascot-and-brand.md).

### 8. Composer and launcher layout — by the room they have

Added 2026-09-29. Nothing here changes what a send does; it changes where the controls sit.

**The composer is a query container.** `.composer-shell` declares `container-name: composer; container-type: inline-size` (`apps/web/app/globals.css:756-761`), so everything inside answers to the composer's own width — beside the rail, in a split pane, on a phone — and never to the viewport. A container cannot query itself, so the shell's margin is the one viewport rule: `var(--space-5) var(--chat-gutter)` (24px all round), and at 639px and under `margin-block` becomes `8px 12px` while `--chat-gutter` drops to 12px (`:765-773`). The margin used to be `mx-6 mb-6 mt-6` utilities on the `<form>` (`chat-composer.tsx:505`); it moved into the class so there is one place that owns it.

**Four layouts, thresholds in container content width** (the shell's box minus 26px of padding and border, which is the toolbar's width). Measured on 2026-09-29 with the Indonesian catalog, the wider of the two: Model 149px, Thinking 137px, Enhance 161px, Send 69px, Attach 32px, 8px gaps.

In compact the chip's border becomes an inset ring so the `<select>` fills all 40px and a tap anywhere on the chip opens the list. The chevron is a separate decorative element, described below.

**The Thinking chevron.** The Thinking `<select>` has `appearance: none` and the pill draws its own chevron: an inline `<svg class="composer-thinking-chevron" aria-hidden="true">` right after the select (`chat-composer.tsx:691-704`; CSS `globals.css:871-915`). The label is `position: relative` in every layout now (it was only the compact one), the chevron is absolutely placed at `right: var(--chevron-inset)` with `pointer-events: none` so a tap or click opens the select beneath it, and the select reserves `--chevron-room` on its right (the 12px box, the inset and 4px of air) so its text never runs under the glyph, in the wide rule and in the compact shorthand alike (`globals.css:897`, `:1006`). The glyph sits 2px inside its 12px box, so the inset is 9px beside the wide layout's 1px border and 10px on the compact inset ring (`:881`, `:986`), and both put the glyph 12px from the pill's outer edge (measured 11.8 to 12 in all four layouts). A disabled select dims itself to 45% and the chevron follows (`select:disabled + .composer-thinking-chevron`, `:912`). The select still sizes to its widest option, so the pill does not change width with the value: 134px wide and medium, 101px compact (`id`; 137 and 103 with the native arrow, whose width varies by platform). Focus, `aria-label` and the testid are untouched.

**One gutter for the Chat column.** `--chat-gutter` is a custom property on `:root` (`globals.css:155`, `var(--space-5)`, 24px) and is `var(--space-3)`, 12px, in the phone block (`:765-768`). Four things read it, so their left and right edges line up at every width: the header row (`chat-header`, `chat-header.tsx:63`, mounted at `chat-session.tsx:399`), the error row under it (`:408`), the message list, which also carries the empty screen's cards (`message-list`, `:427`), and the composer's side margin (`.composer-shell`, `globals.css:759`). One gap is not the token: when the list scrolls, a classic scrollbar (9px in the Browser pane) sits inside its right padding, so cards and messages end that much before the composer does; the overlay scrollbars of a real phone do not.

**The header is one row, and its chips fold into a menu.** `ChatHeader` (`chat-header.tsx:129`, mounted at `chat-session.tsx:399`) is drawn by `components/chat-header.css`: `.chat-header` (`:18-29`) is a non-wrapping flex row with `min-height: 3.5rem` and `padding-block`, never a fixed height. It replaced a wrapping header (`flex-wrap` and a `24rem` container query) that put the chips on their own row under the title and made the header 115px tall on a narrow desk, which had itself replaced a fixed `h-14` row that let a 165px chip spill across the title. There are two modes, `inline | menu`, held as explicit state (`HeaderState.mode`, `lib/chat-header-fit.ts:72-85`) and written to `data-mode` on the root (`chat-header.tsx:63-65`). Inline, the chips sit beside the title as they always did. In the menu, the header holds the title and one `chat-header-menu` button (`chat-header.tsx:74-94`): "Chat details" / "Detail obrolan", a ⋯ icon, `aria-label`, `aria-haspopup="dialog"`, `aria-expanded`, `aria-controls`, at least 40px square (`chat-header.css:51-66`). The chips are then the rows of its panel.

**What decides is measured, never a breakpoint.** `useChatHeaderFit` (`lib/use-chat-header-fit.ts:58`) reads the header's content width, the title's natural width (`h1.scrollWidth`, which counts a truncated title in full), the column gap and the chips' natural width (`controls.offsetWidth`, `:68-102`) and asks `decideHeaderMode` (`lib/chat-header-fit.ts:55-67`). Inline needs the title at `min(natural, 120px)` plus the gap plus the chips; it folds the moment that exceeds the room and unfolds only with 12px to spare (`TITLE_FLOOR_PX` `:17`, `RETURN_MARGIN_PX` `:23`), so a width sitting on the edge cannot flip every frame. With no chips there is nothing to fold and no button. A ResizeObserver on the header, the title and the chips, and a MutationObserver on the chips' children (`use-chat-header-fit.ts:104-127`), run it again, so the usage chip arriving after the first reply, a label growing, a font finishing its load and a resize all refold the same way. A change made from an observer is committed with `flushSync` so no frame is painted in the old mode; the first read runs in a layout effect, which React flushes before paint. It reads `offsetWidth`, not a bounding rect: the desk's enter animation scales the page for a moment, and a scaled rect understates the chips for as long as nothing resizes.

**Each chip is mounted once.** The chips render in one place (`chat-header.tsx:109`), inside one element, `.chat-header-controls`, that never leaves the tree. Inline it is the row beside the title. In the menu it is the panel (open, `chat-header.css:92-107`) or the same row laid out but `visibility: hidden`, `pointer-events: none` and `inert` (shut, `:81-90`, `chat-header.tsx:105`), which keeps its natural width measurable and nothing remounted. The usage chip's one fetch on mount (`GET /api/v1/settings`) is therefore not repeated by a mode change: measured with the real chip, one call at mount and still one after six folds and unfolds. While the panel is open the chips are stacked, so the last natural width stands in until it shuts; a chip set that changes in that time is refitted when it closes.

**A chip's own popover inside a menu row.** The context chip opens a portal popover (`chat-context-chip.tsx:166`) and the account chip an absolute dropdown; inside a menu those would be one focus trap inside another, and the menu's outside-press handler would read the portal as outside. So in the menu a chip reads `ChatHeaderLayoutContext` (`components/chat-header-layout.ts`), drops `aria-haspopup`, and unfolds its details inside its own row (`.chat-header-detail`; `chat-context-chip.tsx:182`, `chat-account-chip.tsx:55`) with the same testids, only while the menu is open. Each chip remembers the header `epoch` it was opened in (`chat-context-chip.tsx:65-66`, `chat-account-chip.tsx:20-21`), and the reducer bumps the epoch on every change of mode or open (`chat-header-fit.ts:109-115`), so the details are closed again by the next change, however it happens, with no effect to run. The usage chip is a link and needs nothing.

**The menu's behaviour** is one reducer, `reduceHeader` (`chat-header-fit.ts:109`). Enter, Space or ArrowDown on the button opens it and puts focus on the first row (`use-chat-header-fit.ts:129-139`); ArrowDown, ArrowUp, Home and End travel the rows and wrap (`nextItemIndex`, `chat-header-fit.ts:153`), and Tab travels them too. Escape closes it and returns focus to the button. A press outside, focus moving outside (Tab off the last row), following the Usage link, or the pane being hidden also close it and leave focus where the person put it. The panel is absolutely placed inside the header, `min(20rem, 100% - 2 gutters)` wide, `max-height: min(32rem, 100dvh - 8rem)` with its own scroll. No portal is needed: it never leaves the box of the desk that clips its ancestors.

### 9. The empty hero — by the room it has, cheap when idle

Added 2026-09-29. `ChatHero` (`apps/web/components/chat-hero.tsx`) is what `ChatLauncher` renders above the intent cards (`chat-launcher.tsx:96`). The old hero was a fixed 34px headline in a `px-6 py-8` panel with seven shapes at fixed percentages, so on a 202px hero the headline wrapped to three lines at full size, the "Kunci model terhubung" pill wrapped to two, the shapes sat on the text, and the panel was 321px tall against a 282px list.

**Three inputs decide how it looks.** The width of the launcher column, which is CSS: `.chat-empty-fit` is the size container (`container-type: inline-size`, `globals.css:1436`) and every fluid length is `cqi` of it, never `vw`. Whether the reader has a fine, hover-capable pointer and has not asked for reduced motion (`heroMotionMode`, `apps/web/lib/hero-motion.ts:18`). And `data-paused` on `.chat-hero`, set while the hero is scrolled out of view or the tab is hidden. The pointer reaches CSS as two unitless custom properties on `.chat-hero`, `--px` and `--py` (-1 to 1, the pointer's place in the hero's rect); nothing else is written per frame.

**What scales** (`globals.css:1739-1895`). Padding is `clamp(8px, 5cqi, 32px)` across and `clamp(12px, 6cqi, 32px)` down; the gaps are `--hero-gap` and `--hero-gap-tight`. The headline is `clamp(1.25rem, 0.8rem + 4.4cqi, 2.5rem)` with `text-wrap: balance`, and its gradient is per line (`box-decoration-break: clone`) so a wrapped line is not a slice of one long gradient (`.chat-hero-title`, `:1834`). The character's button, `.chat-hero-orb` (`:1806`), is `--orb` tall, `clamp(5rem, 24cqi, 8.5rem)`, and 0.72 of that wide, the aspect of the body crop `NX_FULL_TIGHT_VIEWBOX` (`apps/web/components/nultron/nultron-mascot.tsx:37`); the whole Nultron body fills it (`.chat-hero-orb .chat-mascot.nx-root`, `apps/web/components/nultron/nultron.css:49`). The status pill is `clamp(0.6875rem, 0.544rem + 0.88cqi, 0.875rem)`, `white-space: nowrap`, its text a `span.truncate` and its `title` the full line (`.chat-status-pill`, `:1848`; `chat-key-status.tsx`), so it never wraps and gives up characters before it gives up the line. Until the first `GET /api/v1/settings` has answered, the pill is `invisible` and `aria-hidden` (its text a non-breaking space, so its height holds) and there is no Settings button: `gate` is null then, which is "unknown", and painting the needs-key line for those frames told a connected desk to connect a key (`chat-key-status.tsx` `settled`, held by `apps/web/lib/chat-key-status.test.tsx`). Windows 900px tall or less tighten the padding and gaps and take `--orb` to `clamp(4.5rem, 20cqi, 6rem)`; at 860px or less the padding and gaps are 8px and `--orb` is `clamp(3.75rem, 13cqi, 4.25rem)`, 68px on a desk-wide column and 60px on a narrow one (measured at 280 to 728px viewports) (`:1440-1478`). The intent is that an 800px window still fits the hero, both rows of cards and the composer without a scroll. Measured on 2026-09-29 with the whole-body character, fonts loaded, settings fetched and the entrances finished: at 1280 x 860 the hero is 231px with a 68 x 49 character and `message-list` does not overflow; at 1280 x 800 the same hero leaves `chat-empty` 561px tall in a 556px list, so the list scrolls by 5px, which misses that intent; at 1280 x 1000 the character is 136 x 98 and the hero 363px.

**Shapes thin out with the column, in three tiers** (the `chat` layout of `FloatingShapes`, `floating-shapes.tsx:40-77`). Tier 1 (two shapes, in the band either side of the mascot, drawn at 75% size under 26rem) always; tier 2 (three more, outer columns) from a 26rem column, 416px (`@container (min-width: 26rem)`, `:1866`); tier 3 (two more) from 44rem, 704px (`:1877`). A shape that is not shown has `display: none`, so it has no box; its one-time settle plays when the column grows enough to show it. At 280, 320, 375, 728 and 1280 the bounding boxes of the visible shapes were tested against each title line, the pill, the buttons and the orb, and none overlapped. The onboarding hero keeps `layout="hero"`, untouched.

**Interactions**

**Off switches.** Reduced motion: nothing binds (`heroMotionMode` is `off`), `pokeShape` returns without animating, and the reduced block resets the shape transform, the orb's hover and active transforms, the glow and the confetti (`globals.css:2032-2044`), on top of its blanket animation reset. A coarse pointer binds no `pointermove`, so a phone keeps the tap reactions and drops the drift. `lib/motion-tokens.test.ts` still holds: the hero's CSS uses only tokens, keyframes stay on transform and opacity, and every transformed rest state is named in the reduced block.

**The desk-wide switch composes with this, and is now the second line of defence.** `html[data-ambient="paused"]` (`lib/ambient-motion.ts`, mounted in `App`) still pauses whatever a mascot that is not at a job could run whenever the window is blurred, hidden or has had no input for 12 s, on top of the hero's own off-screen pause. The first line is that the hero has no loop of its own: the shapes settle once and rest (second pass of 2026-09-29, § 8 of [`shell-rail-and-workspaces.md`](shell-rail-and-workspaces.md)). Measured on `/chat` with the hero on screen while the pointer is in use: 10.9% of the machine with the shapes looping, 0.67% without (GPU process 0.26, renderer 0.37); idle 0.09% and 0.04%. Map: same page.

**Idle and active cost: no loop.** The hero runs **no infinite animation**. Counted with `document.getAnimations()` on an active `/chat` at 1280: 7 infinite before the second pass (five `nx-bob`, two `nx-spin`; the Nultron mascot has none outside `[data-busy]`), 0 after, and 0 animations of any kind once the entrance is over (about 1.1 s after mount). The hero's mascot has no loop either: idle is still, wave and celebrating are finite clips, and it never carries `data-busy`, so the rule only holds a clip that is playing when the hero leaves the screen. Entrances are deliberately not paused, since pausing one leaves its element at the invisible first keyframe. `lib/motion-tokens.test.ts` ("decoration does not loop") is what keeps a loop from coming back.

**Gotchas.**
- The hero's pause rule, `.chat-hero[data-paused="true"] .chat-hero-panel :is(.chat-mascot, .chat-mascot *)` (`globals.css:1912`), is (0,4,0) and has no `!important`, so a rule with an `animation` shorthand at (0,4,0) or more resets `animation-play-state` and restarts what it paused. The image clip rules (`.chat-mascot[data-clip][data-motion="once"] .nx-strip`, `nultron.css:127`) are exactly (0,4,0), a tie that stylesheet order decides, and the busy loop rules are (0,4,0) to (0,5,0). Nothing depends on that today, because the hero's mascot is never busy and its clips are finite (about 1.1 s); the desk-wide pauses (`globals.css:2011`, `:2019`) use `!important` and reach every mascot whatever the specificity.
- `container-type` on `.chat-empty-fit` makes it the containing block for fixed descendants. Nothing inside it is fixed (the context chip's panel is portaled to `body`).
- The Browser pane reports `document.visibilityState` as `hidden` between tool calls, so a drive that reads the DOM after a call sees `data-paused="true"` and frozen transitions. Force it with `Object.defineProperty(document, "hidden", { get: () => false })` and a `visibilitychange` event, then read the attribute in the same batch as a screenshot.
- `mobile` and any viewport under 768px emulate a touch device, so `pointer: coarse` matches there and the drift is off by design. Drive the pointer effects at the pane's own size or at 1280px.
- Screenshots of an emulated viewport larger than the pane come back scaled down; measure with `getBoundingClientRect` and use the screenshot for the picture.

Proof: `lib/hero-motion.test.ts` (binding, throttling, pausing and teardown against a fake element and browser), `lib/hero-mood.test.ts` (the mood fold), and `lib/chat-hero.test.tsx` (markup hooks in both languages, the container and `cqi` rules, the tier queries, the pause selector and its specificity, the reduced-motion resets, and the header's wrap). ## Gotchas

- **A completed run now writes twice.** `runs.usage` still carries the per-run detail on the run
  row; `recordChatRunUsage` (`packages/host/src/runs.ts:370`, and `:420` on the mid-stream error
  path) also writes a `tenant_usage` row, gated on `finishRun`'s return so one run is exactly one
  row. Anything summing both double-counts chat. See [`tenant-usage-ledger.md`](tenant-usage-ledger.md).

- **The 2026-09-06 changelog block is stale in three places.** It says "Watchdog 60s idle if no events after start" — the budgets are now a model-aware TTFB/idle pair and the TTFB half is a hard cap. It names `chat-send` / `chat-probe` / `chat-fail-closed` as if they were testids — they are **sub-feature names in the verify skill**; there is no `data-testid="chat-send"` anywhere in `apps/web`. And it names `coerceReasoningEffortForModel` as a live step in the wire path; it is not one any more.
- **`coerceReasoningEffortForModel` is dead on this path.** It is implemented, exported from `packages/core/src/index.ts:326` and unit-tested (`packages/core/src/models/reasoning-effort.test.ts:97-107`), but a repo-wide grep at this sha finds no call site outside those two. The "GPT-6 cannot go Off" behaviour it encodes is achieved independently by the allowlist in `packages/core/src/runtime/effort-allowlist.ts`. Treat it as a historical artifact from before the allowlist existed — verified by grep, not by blame.
- **A partial answer is never kept.** On abort or stall, `settleRun` (`packages/host/src/runs.ts:184-192`) sets `settled` and marks the run failed; every `persistAssistant()` call is behind an `if (settled) return`. Whatever the model streamed is discarded. Only an upstream error while `settled` is still false can persist partial text.
- **The renderer's own watchdog never leaves first-token mode.** `readSse` calls `dog.touch()` only (`apps/web/components/chat-composer.tsx:421`, `:488`); `touchOutput()` is never called on this path. Since `streaming` only flips in `touchOutput`, the client-side deadline stays `startedAt + ttfbMs` for the whole run, and repeated touches re-arm a timer that fires at the same instant. A genuinely long, actively-streaming answer can therefore be aborted client-side. The host-side guards do call `touchOutput` (`packages/host/src/runs.ts` via `isRunOutputEvent`), so this asymmetry is renderer-only. **Treat as a finding, not a design.**
- **`gateway_blocked` is swallowed in Chat.** The host emits it as a flat body with `error` as a *string*, precisely so `parseGatewayBlocked` (`apps/web/lib/gateway-gate.ts:145`) can read it — but that parser is only wired into `settings-page.tsx` and `onboarding-screen.tsx`. The composer does `payload.error?.message ?? t("chat.error.runFailed")` (`apps/web/components/chat-composer.tsx:413`, `:480`), and `.message` on a string is `undefined`, so a blocked gate shows the generic "run failed" copy in Chat. **Also a finding.**
- **Probing has no UI.** `ChatComposer` declares an `onProbing` prop with an `attempt` / `attempts` / `message` payload (`apps/web/components/chat-composer.tsx:42`) and never calls it — `run.probing` is handled by calling `onStarted()` and dropping the payload (`apps/web/components/chat-composer.tsx:153-155`); `ChatSession` never passes `onProbing` either. The locale string `chat.error.couldNotReach` exists in both catalogs with zero references. This is why `features/chat.md` requires that probe copy must *not* appear on the frontend — it cannot.
- **`message-output` mounts twice per turn**, once live and once persisted, in different component subtrees. A test that waits on the testid can observe two mount cycles for one message.
- **Three watchdogs, different semantics.** The inner one is retried; the outer one is not. The outer guard is touched by *every* event including `run.probing`, so it mostly protects against total silence rather than against a retry loop.
- **`finishRun`'s `WHERE status='streaming'`** (`packages/host/src/threads.ts:327`) is the real race resolver between watchdog, abort and completion; the in-process `settled` flag is a fast-path mirror of it, needed because `finishRun` cannot be called before `insertRun` returns a `runId`.

## Why

**Why the first-token budget is a hard cap rather than something a frame can extend.** `[Direct]` `docs/internal/0.14.26-changelog.md:121` records the bug: `AiSdkRuntime.consume` fed the watchdog from every `fullStream` part, and the AI SDK enqueues `step-start` on the provider's first chunk while `@ai-sdk/openai` emits `response-metadata` on the gateway's very first SSE frame — "so half a second in, before any token, the 120 s first-token budget was swapped for the 60 s idle one (the reported error is the *idle* wording, which proves a part had already landed)." `[Direct]` `docs/internal/0.14.26-changelog.md:139` records the review fix: "the first-token budget is a hard cap again (a liveness-only frame no longer pushes it out, so a gateway that heartbeats without answering cannot hold a run open — one rule now in `streamWatchdogDeadline`, used by both the checker and the armed timer)." The code comment at `packages/core/src/runtime/stream-watchdog.ts:82-86` says the same. **Confidence: high.**

**Why `QUIET_REASONING_FAMILY` exists.** `[Direct]` `docs/internal/0.14.26-changelog.md:123`: the resolved Finance/Documents/Market default is `deepseek-v4-flash`, DeepSeek V4 thinks on by default, "its thinking streams as `delta.reasoning_content`, which AI SDK 4 drops (the same gap `packages/core/src/runtime/minimax-compat.ts` was written for), so nothing at all reached the watchdog for the ~50 s the model spent drafting." The fix was to widen the family, not to change any model default (`:125`). **Confidence: high.**

**Why Chat is excluded from the job thinking knob.** `[Direct]` the type comment at `packages/core/src/runtime/types.ts:54-58` states it, and `packages/core/src/runtime/ai-sdk-runtime.ts:274` carries the matching inline note. `[Supported]` `docs/internal/blockers-2026-09-15.md:226` closes blocker P1 with "Jobs send `{"reasoning_effort":"low"}` and nothing else (`packages/core/src/models/job-thinking.ts`, applied in `ai-sdk-runtime.ts` only when `execute` carries `jobMode`; Chat's body unchanged)." The reason to keep them apart is that Chat's effort is a user choice with a visible picker, and overriding it to `low` would silently disobey the user. **Confidence: high for the mechanism; the "would disobey the user" reading is `[Inferred]` from the picker's existence.**

**Why the job knob is `reasoning_effort: "low"` and not thinking-off.** See [`finance-parse-and-generate.md`](finance-parse-and-generate.md#why) — the same decision, recorded there because that is where it was driven.
