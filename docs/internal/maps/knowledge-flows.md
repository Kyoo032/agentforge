## Overview

The owner's question is "how does each knowledge go to the Knowledge Base?". This page answers it for fifteen surfaces at once: the eleven modes, the three manual entry points on `/knowledge`, and Soul/Memory — which look like knowledge and are not sources at all.

The machinery underneath (chunker, embedder, guard rule set, schema, backend registry, reindex) is [`knowledge-ingest-loop.md`](knowledge-ingest-loop.md); the `/knowledge` page itself is [`knowledge-base-page.md`](knowledge-base-page.md). This page does not repeat either. What it adds is the **per-surface** truth: what triggers a card, what text ends up inside it, what is silently left out, who can read it back, and what happens on delete.

Three things surprise everyone. **Every automatic card in the product goes through one function**, `upsertWorkSource` — there is no second writer. **Only Chat retrieves**: ten job modes write cards and read none, so a knowledge answer inside Finance does not exist. And **the card is text, never the bytes**: a Videos card holds the prompt, not the mp4; a Data card holds the model's evidence tables, not the dataset.

### 1. The shared funnel — `upsertWorkSource`

Every automatic card in the eleven mode rows above, without exception, is one call to `upsertWorkSource` (`packages/host/src/knowledge-ingest.ts:24`) with a `WorkCard`. There is no second writer. In order (`knowledge-ingest.ts:27-83`):

1. `scanInjection(card.title)` — a title that trips the guard is **replaced by the mode name** (`:28-29`), so one poisoned thread title cannot block every later card of that thread.
2. `maskPii` over **title, prompt and body field by field**, then `renderWorkCard` (`knowledge-ingest.ts:37-43`). `renderWorkCard` (`packages/host/src/work-cards.ts:50`) emits `# <title>` / `Mode: <type>` / `Model: <model>` / `Pointer: <thread|artifact|media>:<id>` / `Prompt: <≤1 200>`, then the body, capped so header + body ≤ `WORK_CARD_BODY_MAX = 8_000` (`work-cards.ts:22`, `:24`). Over-cap text gets `\n[truncated]`. **Field-by-field is new on 2026-09-17**: masking the *rendered* string ate the host-generated `Pointer:` UUID, because a UUID whose middle groups are all decimal matches the phone pattern.
3. An empty rendered card → `{status:"skipped"}`, no row at all (`:44-46`).
4. `findSourceByOrigin` (`knowledge.ts:210`, working tree) — **idempotent per `(workspace, origin.kind, origin.id)`**. An existing row is reused by id; only the first write is `created`.
5. `scanInjection(card.body) ?? scanInjection(card.prompt ?? "")` (`:61`). A hit writes a `Failed` row reading `injection_blocked (rule: …)` through `markSourceFailed` (`knowledge.ts:384`, working tree), and that source is never retrievable. The owner's `injectionGuardBypass` skips both scans (`:27`, `:93-99`).
6. `indexKnowledgeSource` (`knowledge.ts:365`, working tree).

It never throws and it never fails the work that produced it: an index error leaves a `Failed` row and the generate still returns its result.

**Idempotence is per origin id, not per run.** Only Chat rewrites in place, because a thread keeps one id across turns. Every Finance / Data / Legal / Market / Documents / Presentation generate mints a **new** artifact, so a second run of the same job adds a second card rather than replacing the first. `knowledge-ingest-loop.md`'s "re-running a thread rewrites one row instead of piling up duplicates" is true for `origin.kind = "thread"` and for nothing else.

### 2. Manual sources take the other door — `indexSource`

Paste, File and URL never build a work card. All three are gated (`requireGatewayAllowed` at `handlers/knowledge.ts:376` and `:409`, working tree) and all three reach `indexSource` (`knowledge.ts:430`, working tree) or, for a file, `indexKnowledgeSource` directly. The guard runs over the **raw name and then the text** (`injectionRule`, `knowledge.ts:421`, working tree) — the raw name, not the sanitized one, so stripping a leading `###` cannot also strip the rule that would have caught it. `origin` is `null` for all three, which is why nothing ever cascades to them and the orphan sweep cannot see them.

**What a `document` upload actually runs (new on 2026-09-17).** `documentText` (`knowledge-extract.ts:126`) hands the bytes to `extractFile` (`packages/host/src/file-extract/index.ts:171`), the one shared local file → Markdown pipeline. It loads `@firecrawl/anydoc` through `createRequire` (`file-extract/anydoc.ts:53-67`); if that native binding is missing on this platform the failure is logged once and the upload degrades to the extractors this repo already shipped (`tryLoad`, `index.ts:118-125`). `detectFormat` (`file-extract/detect.ts:77`) reads the extension **and** the first bytes and refuses `format_mismatch` when they disagree, so a workbook renamed `.csv` never reaches the CSV parser. The caps are borrowed, not invented (`file-extract/limits.ts`): `FILE_EXTRACT_MAX_BYTES = min(PDF_MAX_BYTES, FINANCE_IMPORT_MAX_BYTES)` = **25 MB** (`limits.ts:22`), `FILE_EXTRACT_TIMEOUT_MS = PDF_TIMEOUT_MS` = **20 s** (`:25`), Markdown cut on a line boundary at `KNOWLEDGE_TEXT_MAX_CHARS` = **2 000 000** chars with `meta.truncated` set (`:28`, `index.ts:104-111`), at most **200** tables (`:31`), each capped at the spreadsheet import's 5 000 rows / 100 cols / 160 cell chars (`:34-40`). The fallback path only covers `pdf`, `docx`, `xlsx`, `csv` (`file-extract/fallback.ts:77`); a `.pptx` / `.odt` / `.rtf` / `.epub` on a binding-less platform is `unsupported`, exactly as it was before the converter existed.

**Nothing in that path opens a socket.** anydoc's one network option is `ocr: 'hosted'`, which uploads the document to Firecrawl Parse; `anydoc.ts` never constructs an options object at all — `toMarkdownBytes(bytes, format)` is called with exactly two arguments (`anydoc.ts:72-86`) — and never reads a `FIRECRAWL_*` variable. A scanned PDF is refused locally as `needs_ocr`, and the sentence the owner sees says so (`file-extract/errors.ts:52`). `file-extract/privacy.test.ts` asserts the sockets stay shut for every format including that refusal, and `file-extract/no-hosted-ocr.test.ts` greps the repository so a later call site cannot add the option back. Each of the ten `FileExtractErrorCode`s (`errors.ts:12-32`) becomes an `ApiError` named `document_<code>` (`knowledge-extract.ts:121-123`), `413` for `too_large` and `400` for the rest (`:119`), so a source row records *why* it could not be read.

The fourth entry point on that route is `{artifactId}` → `sendArtifactToKnowledge` (`handlers/knowledge.ts:65`, working tree) — the "Send to Knowledge Base" button that five studios mount from one component. It is idempotent against the auto-ingest origin (200 + `alreadyIndexed: true`) and, **as of the working tree today**, resolves the work type from the artifact's own mode first: `workTypeForArtifact` (`handlers/knowledge.ts:99`, working tree) is `artifactModeToWork(mode) ?? KB_TYPE_TO_WORK[kbType] ?? "Documents"`. Before that fix the client label won, which is how a `market/briefing` sent with `kbType="Brief"` filed itself as `Finance`.

### 3. Chunk, commit, embed

`indexKnowledgeSource` sanitizes the name, then `chunkKnowledgeText` (`packages/host/src/knowledge-text.ts:141`) splits heading-aware with `CHUNK_TARGET = 800` / `CHUNK_OVERLAP = 120` (`:53`, `:56`). `replaceSourceRows` (`knowledge.ts:269`, working tree) commits the source row and one `knowledge_chunks` FTS5 row per chunk in **one immediate transaction, before embedding** — which is why keyword search answers even when the embedding call failed and the row still reads `Indexed`. Vectors follow in batches of 16 against the pinned gateway. The rest is [`knowledge-ingest-loop.md`](knowledge-ingest-loop.md).

In practice: a media card is one chunk, a Chat turn one, a short document two or three, a three-slide deck four or five (the speaker notes dominate), and a Market briefing twelve — which is the cap, not the briefing.

### 4. Tenant scoping

Everything is parameterized by `tenant.workspaceId` in application code; `knowledge_chunks` is a bare FTS5 virtual table with `workspace_id` as a plain column, no foreign key and no row-level security (`packages/db/src/ensure-schema.ts:602-606`). The guarantee is the tests, not the schema.

Two things on this page are **organization**-scoped instead: the raw bytes a file upload leaves on disk (`knowledge.ts:509`, working tree), and the `media` table the sweep consults for Images / Videos / Edit cards (`ORIGIN_OWNERS`, `knowledge.ts:626`, working tree — the `media` table has no workspace column). Everything else on the path is per-desk.

### 5. Retrieval — Chat, and only Chat

`knowledgeInjection` (`knowledge.ts:822`, working tree) has exactly two callers: `startModalityRun` (`packages/host/src/runs.ts:153`), whose result is concatenated onto the agent's system prompt at `:157`, and the read-only popover route `GET /api/v1/knowledge/context` (`handlers/knowledge.ts:312`, working tree). Since `handleRun` serves `/runs/text`, `/runs/image` and `/runs/video` (`router.ts:193-195`), the retrieving surface is precisely "a run inside a Chat thread, of any input modality" — not the `chat` product mode as such.

- **Top-k is a hardcoded `4`**, in both `knowledgeInjection` and the `retrieveChunks` default (`knowledge.ts:770`, working tree). No setting, no query parameter, no per-mode override. An empty query skips retrieval entirely.
- **Anti-loop.** `excludedSourceIds` (`knowledge.ts:791`, working tree) resolves the asking thread's own card by origin and excludes it — which is why proving retrieval of a Chat-authored card needs a *fresh* thread.
- **Both engines always run.** `SqliteBuiltinBackend.retrieve` (`packages/host/src/knowledge/backends/builtin.ts:249`) runs a cosine scan of `knowledge_vectors` and an FTS5 `bm25(knowledge_chunks)` query and fuses them with `fuseRrf` (`:154`, `RRF_K = 60` at `:133`). "FTS fallback" is not a branch: it is one of two lists that always runs, and it carries the query alone whenever the vector side returns nothing. `fusedMode` (`:199`) labels the outcome `hybrid` / `rag` / `fts` / `none`, which `sourcesDetail` (`knowledge.ts:814`, working tree) turns into the popover's `"<k> chunks · <mode>"`, with ` (degraded)` when the desk's own engine is not the one that answered.
- **The `[n]` markers are positional.** Each hit renders as `[<index+1>] <sanitizeSourceName(name)>\n<body>` in `knowledgeInjection`. The name is sanitized *again* at render time so a row written by an older build cannot forge a citation line, and nothing name-matches — the number is order of retrieval.
- **`cites` edges.** After a run that completes (or that broke mid-stream but saved partial text), `runs.ts:370` and `:374` call `recordRetrievals` (`packages/host/src/knowledge-retrievals.ts:38` — one `knowledge_retrievals` row per injected chunk plus a `retrieved` graph edge) and `recordCites` with `citedSources` (`packages/host/src/knowledge-cites.ts:64`), which parses bare `[n]` with `/\[(\d+)\]/g`, skips fenced code blocks whole including an unterminated fence, takes `chunks[marker - 1]`, dedupes by source, and **silently drops a marker past the injected count**. `[S1]`, `[1,2]` and `[0]` are not markers. A failed or aborted run records neither.
- **Graph expansion is off.** `RetrieveOptions.expand` is built and unit-tested; there is no Settings key and Chat never passes it. The backend registry is a hardcoded `return "builtin"`.

| A knowledge source | `DELETE /api/v1/knowledge/sources/:id` (ungated) → `deleteSource` (`knowledge.ts:601`, working tree) | chunks, vectors, **its graph node and edges, its retrieval rows** (`dropSourceTraces`, `knowledge.ts:591`, working tree), the source row, and **the raw upload on disk** (`removeStoredUpload`, `:460`) | nothing on the knowledge side |
| A thread | `DELETE /api/v1/threads/:threadId` → `deleteSourceByOrigin(…, {kind:"thread"})` (`threads.ts:139`) | the thread's `Chat` card in full, with its traces | the thread's own graph node, unless `sweepOrphanGraph` reaches it |
| An artifact | `DELETE /api/v1/artifacts/:artifactId` → `deleteSourceByOrigin(…, {kind:"artifact"})` (`handlers/artifacts.ts:40`) | the artifact's card — auto-ingested or button-sent, both write the same origin row, so one delete covers both | — |
| A media item | **no route exists**; the orphan sweep is the only reconciler | — | the card, until the sweep sees the `media` row is gone |
| A dataset | `DELETE /api/v1/datasets/:datasetId` (`router.ts:229`) | the dataset | the `Data` card, until its artifact is deleted and the sweep runs |
| A legal matter | `DELETE /api/v1/legal/matters/:id` → `rmSync(dirFor(...))` (`packages/host/src/legal/store.ts:169`) | the matter directory | the deliverable artifacts and the `Legal` card, until those artifacts are deleted and the sweep runs |

**The sweep.** `sweepOrphanSources` (`knowledge.ts:671`, working tree; `sweepOrphanThreadSources` at `:697` is the old name and still exported) runs on every `GET /api/v1/knowledge` (`handlers/knowledge.ts:131`, working tree). It drops work cards whose subject is gone for **all three origin kinds** — `thread`, `artifact` and `media` (`ORIGIN_OWNERS`, `:626`) — takes their traces and stored uploads with them, and then calls `sweepOrphanGraph` (`packages/host/src/knowledge-graph-prune.ts:108`) to repair nodes, edges and retrieval rows left by builds that had no cascade. `orphansOfKind` returns `null` rather than an empty list when an owner table cannot be read, so an unreadable table can never be mistaken for "nothing owns these rows". **All of this landed on 2026-09-17**; at `01ea70a` the sweep was thread-only and nothing ever deleted from `knowledge_graph_*` or `knowledge_retrievals`.

| Injection hit in a card's **title** | `knowledge-ingest.ts:28-29` | not a failure — the title is replaced by the mode name and the card indexes normally |

| Scanned PDF sent through the converter | `extractFile` → `needs_ocr` (`file-extract/errors.ts:51-54`) | 400 `document_needs_ocr`, "OCR is not available locally yet, and nothing was sent anywhere." No upload, no hosted OCR, no row |
| Artifact could not be saved | the `if (artifactId)` guard in every job harness | no card at all, silently — the studio still shows its result |
| Embedding call fails mid-batch | `knowledge-embed.ts` | the whole source degrades to `stub-fnv-32` vectors and a five-minute breaker opens workspace-wide; the FTS rows are already committed so the row still reads `Indexed` |
| Job cancelled (`throwIfJobAborted`) | before the persist step | no artifact, no card |

## Gotchas

- **Several bugs described by the 2026-09-17 knowledge-flow drivers were fixed in the tree the same day. Do not read this page as saying they are permanent.** Landed while it was being written: **Market auto-ingest** (`saveBriefing` now calls `upsertWorkSource`, and `Market` is a work type); **the Brief→Market filing bug** (`workTypeForArtifact` asks the artifact's mode first; `Memo` / `Playbook` now map to `Legal`); **the Finance regenerate duplicate** (regen carries the artifact id back and re-upserts, `finance-generate.ts:291`); **the graph / retrieval / media / artifact orphan sweeps** (`sweepOrphanSources` + `knowledge-graph-prune.ts`); **the `.html` upload keeping its markup** (`sourceKind` routes html to `htmlToText`); **the raw upload bytes surviving a delete** (`removeStoredUpload`); **`201 Created` for a failed upload** (now a structured 4xx); and **`maskPii` eating the card's own `Pointer:` UUID** (masking is field-by-field now). **Still open at the time of writing:** the Chat card's frozen title, the duplicated prompt and wrong duration on media cards, Documents / Presentations rewrites never persisting, Legal indexing one of five deliverables, and the 8 000-char cap eating a Market briefing's provenance. Re-check before quoting any of them — this page was written against a tree that moved four times in an hour.
- **The host reads ten more file types than the file picker offers. Finding.** `sourceKind` routes `.pptx .ppt .xlsx .xls .ods .odt .odp .doc .rtf .epub` to the converter (`knowledge-extract.ts:56-67`, `:83`) and `.html` / `.htm` to `htmlToText` (`:80`), but `apps/web/components/knowledge-page.tsx:424` still sets `accept=".txt,.md,.csv,.json,.pdf,.docx"` plus those six mimes. The OS file dialog therefore hides every format that landed today, and the new `unsupported_content_type` sentence advertises types the picker will not let a user choose. The route itself accepts them — a drag-drop or a direct `POST` works — so this is a picker that is behind its host, not a missing feature.
- **A converted document is indexed as prose; its tables are dropped.** `extractFile` returns `markdown`, `text`, `tables` and `meta`, and `documentText` keeps `extracted.text` alone (`knowledge-extract.ts:126-131`). A workbook's sheets survive only as the flattened text of the Markdown tables; nothing on the knowledge path reads `tables`, `meta.sheets` or `meta.truncated`, so a document cut at the 2 000 000-char cap is indexed silently with no marker of its own.
- **`.pdf` and `.docx` deliberately did not move to the converter.** The file's own header says why (`knowledge-extract.ts:9-13`): the knowledge index, its page markers and its `pdf_*` / `docx_*` failure codes are built on the existing parsers, and the point of the change was to add formats, not to re-cut every document already indexed. So one upload dialog now has two readers behind it with two different failure vocabularies — `pdf_*` / `docx_*` for the two old formats, `document_*` for the ten new ones.
- **The card is text; the bytes stay where they are.** A Videos card is its prompt. A Data card is the model's evidence tables, not the dataset. A Legal card is the red-flags markdown, not the `.docx`. Chat retrieves cards, never files.
- **`maskPii` used to eat the card's own `Pointer:` line.** Masking ran over the rendered string, headers included, and `PHONE_RE` matches a dash-separated run of 10–15 digits, so a UUID whose middle groups are all decimal came back as `Pointer: artifact:b73b[phone]-bde3-…` in the *indexed* copy while the database id stayed intact — silent, the card still read `Indexed`, and the corrupted copy was the one Chat was given. Fixed on 2026-09-17 by masking title / prompt / body separately (`knowledge-ingest.ts:37-43`); the header lines are host-generated and carry no user PII.
- **A Chat card's name and its body drift apart permanently.** The name follows the thread title on every upsert, but a thread title is itself derived once from the first user message and never changes, while the body is replaced on every completed turn with that turn's exchange only. The title also sits *inside* the indexed chunk as the `# <title>` header, so stale first-turn wording keeps scoring FTS hits for questions the card can no longer answer — and `[n] <name>` is what a citation shows the user.
- **A rewrite is the one version that is never kept.** Documents section regen and Presentations slide regen return a merged draft and persist nothing — no artifact write, no `upsertWorkSource`, and the DOCX / PPTX routes are pure bytes routes. The user downloads the good file, and Chat then retrieves the first draft and cites it as this workspace's document. No error, no "unsaved" state, and closing the tab loses the rewrite.
- **Only Chat retrieves, and that is still true after today's fixes.** Ten job modes write cards and call `knowledgeInjection` zero times. `docs/product-modes.md:91`'s "other job modes will share the same retrieve later" is entirely unstarted — there is no partial implementation behind it.
- **The 8 000-char cap is sized for a Chat exchange.** A Market briefing renders ~39 KB with the watchlist, macro, chart, headline and `## Sources` tables **last**, so the auditable half is exactly what the cap eats. A Chat answer citing that card can never reach the provenance the Market guard worked to attach.
- **Legal indexes one of five deliverable kinds.** `knowledgeCard` takes `red-flags`, else `issues-memo`, and nothing else (`legal-generate.ts:184-187`). A matter whose deliverables are redline / deviation-report / executive-summary produces artifacts and **no card at all**, and the studio's button is disabled in that state, so there is no manual escape hatch. When both are produced, the memorandum — the longer document — is the one that is not indexed.
- **Every media card contains its prompt twice** — once in the body (`mediaWorkCard`, `work-cards.ts:84-86`) and once in the rendered `Prompt:` header, one capped at 1 200 and one not. Since a media card is essentially nothing but its prompt, this doubles its term frequency against `bm25`, so media cards rank higher on their own prompt words than a single-copy source would.
- **A video card records the requested duration, not the generated one** — `snapVideoSeconds` goes to the tool (`studio-generate.ts:229`), the raw `body.seconds` goes to the card (`:261`) — and the common `undefined` case is falsy, so `mediaWorkCard` drops the `Duration:` line entirely for a default-length clip that had a definite one.
- **A pasted source is unreachable by any cascade.** Paste, File and URL have `origin: null`, so the sweep cannot see them and no delete anywhere else can reach them. Remove on `/knowledge` is the only path, and for a paste created from the UI every row is named "Pasted notes" / "Catatan tempelan", so telling two of them apart means opening them.
- **Two labels behave one way and four the other.** `KB_TYPE_TO_WORK` answers for `Dossier`, `Analysis`, `Brief`, `Memo` and `Playbook` and maps `Paste` to `null`; it is now only consulted when the artifact's own mode names no desk. The label is still what a text-only send (no `artifactId`) stores verbatim, so the same word means different things on the two branches of one route.
- **Soul is the one un-guarded string in the system prompt.** `scanInjection` runs on every source and every work card; `putSoul` and `addMemory` do not. Defensible — it is the owner's own typing — but it should be a deliberate choice rather than an accident.

## Why

**Why only Chat retrieves.** `[Direct]` `docs/product-modes.md:91` states the present tense plainly: "Chat injects soul + pinned memories + RAG retrieve now; other job modes will share the same retrieve later." `[Supported]` a repo-wide grep for `knowledgeInjection` / `retrieveChunks` outside tests returns `runs.ts:153`, the popover route, `knowledge.ts` itself and the self-check, and nothing else — so the sentence is accurate about today and unfulfilled about tomorrow. **Confidence: high.**

**Why the guard refuses rather than sanitizes.** `[Supported]` `docs/internal/unreleased.md`'s 2026-09-08 (night) entry records the hardening round that introduced it — "plaintext PII / injection text in work cards (mask + guard)" — and [`knowledge-ingest-loop.md`](knowledge-ingest-loop.md) records the resulting shape: a tripped source is `Failed` and invisible to retrieval, with no sanitized-and-indexed outcome. A card is read back as a *trusted* block inside the system prompt, so a partially-cleaned card is worth less than no card. **Confidence: high for the mechanism; the "trusted block" reading is `[Inferred]` from where `## Retrieved sources` sits in the assembled prompt.**

**Why Market had no automatic card until 2026-09-17.** `[Supported]` the knowledge-flow pass recorded it as finding M1 in `docs/internal/unreleased.md` and re-proved it live: `market-generate.ts` did not import `knowledge-ingest` at all, while Finance, Data and Legal all called `upsertWorkSource` at the same point in their save step. Nothing in the tree or the changelogs argues it was deliberate, and the fix landed the day it was found. **Confidence: medium — recorded as an omission, not a decision; no source states an intent either way.**
