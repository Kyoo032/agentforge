## Overview

New models reach the Chat picker by themselves: `refreshModelCache` reads the gateway's `GET /v1/models` (`packages/host/src/selectable-models.ts`). What the picker cannot say is **how a model wants to be called**: which wire, which Thinking levels it accepts, how Off is spelled, whether a job should ask it to think less. That used to be guessed from name regexes scattered over six files, and an id from an unknown family got the pass-through Completions profile, so Extra, Max, Ultra or Off could make the gateway answer 400, which nothing retried.

Two things replace that. **One table** declares how each known model is called, and every caller asks the same lookup, `modelPolicy(id)`. **One retry** in the runtime both Chat and every job harness share: when the gateway refuses the Thinking parameter before anything came back, the runtime tries once with a safer shape and remembers, for a while and for that tenant, what worked for that model.

It is not a catalog (the picker's list still comes from the gateway), not the recommendation lists (`CHAT_DEFAULT_PREFERENCES` and the per-mode lists live in their own files, § 7; the table only says whether each id they name is known), and not an entitlement check (the gate is [`settings-and-gateway-gate.md`](settings-and-gateway-gate.md)).

## How it works

### 1. The table and the lookup

`MODEL_POLICY_TABLE` (`packages/core/src/models/model-policy.ts:177`) is an ordered list; the first entry whose exact `ids` or `pattern` matches the **bare id** (vendor prefix, case and outer space stripped by `bareModelId`, `packages/core/src/models/request-constraints.ts:13`) wins. `modelPolicy` (`model-policy.ts:424`) returns one frozen answer: `key`, `known`, `wire`, `efforts` per wire slot, `off`, `reasoning`, `jobThinking`, `tier`, `bestFor`, `verified`. Tier and best-for are per-id facts kept in `gateway-roles.ts`; `roleFor` (`:392`) lays them over the behaviour entry, dated snapshots included (eight digits: `-260910` is not a date to it), so the lookup is still the one answer. An id the role table has no line for gets Image, Video or Audio from `mediaKind` (`mediaHint`, `:401`) and General chat otherwise, which is what image and video ids said before 2026-09-30. A role never makes an unknown id everyday: anything the table does not know is `advanced`, so it cannot reach Recommended.

### 3. From the request to the wire

- **Chosen or defaulted.** `readReasoningEffortChoice` (`reasoning-effort.ts:77`) returns the level and `explicit`: true only when the body carries a level or `thinking: false`. `readOptionalReasoningEffort` (`:105`) is unchanged in signature. Chat's `startModalityRun` passes both (`packages/host/src/runs.ts:138`, `:297`); the field is `reasoningEffortExplicit` on the runtime input (`packages/core/src/runtime/types.ts:43`). A job passes neither, so its level is never "chosen". **From Chat the renderer decides what the body carries:** the Thinking picker shows Normal from the start, but the composer spreads `thinkingRequestFields(reasoningEffort, reasoningEffortChosen)` into the run body (`apps/web/components/chat-composer.tsx:415`, `:481`; `apps/web/lib/chat-thinking.ts:67`), which is `{}` until the person has picked a level (or restored one they picked earlier from `localStorage`, `chat-thinking.ts:39`, `chat-session.tsx:153-166`). So an untouched Chat reaches the host as `medium`, `explicit: false`, and an unknown model is sent no effort (`packages/host/src/runs-reasoning-effort.test.ts`; nothing new in the host, the mechanism was already there).
- **The plan.** `AiSdkRuntime.execute` builds one `EffortState` per run, scoped to the tenant (`packages/core/src/runtime/ai-sdk-runtime.ts:223-231`); a job on a quiet family feeds the knob's level in as the requested one (`jobKnob`, `:220`), so a level the gateway refuses can step down and stay down instead of the knob rewriting it. `planEffort` (`packages/core/src/runtime/effort-plan.ts:79`, `levelFor` `:60`, `withLearned` `:41`): a learned drop gives no level; an `explicit_only` model with nothing chosen gives none; Off on an `omit` model gives none; otherwise the request snaps to the wire's list, then a learned swap for that exact level applies, then a learned ceiling caps it. **No level means no effort parameter at all.**
- **Every request reads the state.** The openai fetch wrapper (`ai-sdk-runtime.ts:288`) writes the level per URL (`:298-321`): on `/chat/completions` it writes `reasoning_effort` or removes it (`withoutReasoningEffort`, `reasoning-effort.ts:233`) and merges the rest of a job knob; on `/responses` it makes sure the body has `reasoning: { effort, summary: "auto" }` (Off is `{ effort: "none" }`, no summary), which `@ai-sdk/openai` 1.3.24 writes itself only for ids that start with `o` or `gpt-5` (`getResponsesModelConfig`, `node_modules/@ai-sdk/openai/dist/index.js:2623`; the block itself `:2118`). For any other id the SDK left the level out, so `applyReasoningToResponsesBody` (`reasoning-effort.ts:208`) adds the block right after `input` when it is missing, in the same shape and place as gpt-5.x, from the same plan (Off floors to `low` for GPT-6 Astra and any GPT 6 id without an entry, and is sent as `none` for Luna and Sol; a heal steps it down). A body that already has a `reasoning` block is the SDK's and is returned untouched, so gpt-5.x, o-series and the recorded bodies did not move. The Messages and generateContent wrappers pass the level, or `undefined` to leave `thinking` and `thinkingConfig` alone (`:361`, `:396`, `chat-wire.ts:210`, `:260`); the SDK's own reasoning options are built in `consumeOnce` (`:475-480`) with `omitReasoning` (`api-mode.ts:75-77`), which beats even Responses' `medium` default.
- **What else the SDK gates on the id (GPT-6 against gpt-5.6 on Responses).** Read against the same file: the `reasoning` block (fixed above); the system message's role (`developer` for `o*` and `gpt-5*`, `system` otherwise, `:1806-1830`); `temperature` and `top_p` are stripped for reasoning ids (`:2132-2148`). The runtime sets no temperature on a Responses call and `checkModelRequest` drops every sampling key on `/responses` anyway (`request-constraints.ts:79-80`), so the last is moot. **The role is the one real difference left**: a GPT-6 Responses body carries `{"role":"system"}` where gpt-5.6's carries `{"role":"developer"}`. The Responses API accepts `system` for every model and reads it as `developer` for a reasoning model (OpenAI's documented behaviour; not re-driven against this gateway, and not clearly wrong), so it is recorded (`ai-sdk-runtime-responses-reasoning.test.ts`, "GPT-6 against gpt-5.6 on the wire") and not changed. If a live GPT-6 call ever answers 400 to `system`, that test is where to start. On Completions (only reachable by forcing the wire) the same gate also picks `system` over `developer`, `max_tokens` over `max_completion_tokens` (the runtime sets neither) and whether tool schemas are strict (`supportsStructuredOutputs`, `:378`).

### 4. When the gateway refuses the parameter

The hook is `AiSdkRuntime.stream` (`ai-sdk-runtime.ts:427`), the one place Chat and every job harness (`runJobAssistantOnce` → `runtime.execute`, `packages/host/src/job-regen.ts`) share:

1. The three fetch wrappers throw `GatewayHttpError` (`ai-sdk-runtime.ts:209`; `packages/core/src/gateway-http-copy.ts:74`): the sentence for the person as its message, the status and the raw body as a **non-enumerable** property, so the body never reaches a log line or a serialised error. `consume` keeps them on the outcome (`:704` for a stream error part, `:747` for a throw) as `failure`.
2. After the first call and any wire fallback, `if (first.failure && !first.text && !first.tooled && !first.thinking)` (`:530`) then `effort.heal(...)` (`:531`). **Never after a token, a thinking delta or a tool call** (a tool call in step 1 followed by a 400 in step 2 is left alone: the tool ran), and never for anything but a 400 or 422 whose text names the parameter and refuses it. The classifier reads the error's message, parameter name and code, never its `type` (every 400 is filed under `invalid_request_error`), and refuses context length, a bad key, a missing model, a tools-on-Completions message, a malformed body and every 401, 403, 404, 429 and 5xx (`classifyEffortRejection`, `packages/core/src/runtime/effort-selfheal.ts:101`; `NOT_ABOUT_EFFORT` `:42`, `refusalText` `:75`).
3. A rejected **value** ("Unsupported value: 'xhigh' … Supported values are …", Google's "Budget 0 is invalid") steps the level down one within the wire's allowed list; a rejected **parameter** ("Unsupported parameter: 'reasoning_effort'") or a level already the lowest drops it (`saferEffortAction`, `:124`; the two patterns `VALUE_REJECTED` `:58` and `PARAMETER_REJECTED` `:62`). One retry per run (`effort-plan.ts:127`); a second refusal is the answer.
4. `effort.settle(!first.failed)` (`ai-sdk-runtime.ts:538`): only a retry that answered teaches anything (`limitFromHeal`, `effort-selfheal.ts:147`), and one `console.warn` line says what happened: model id, requested level, learned level, nothing else (`gateway: effort limit learned model=… requested=ultra learned=max`; a retry that did not help says so and learns nothing). **What it teaches is as narrow as the refusal:** a refused parameter teaches "this model takes none" (`drop`); a refused level from Deep up teaches a ceiling, since a gateway that refuses Extra refuses Max and Ultra; a refused level below that (Off, Light, Normal) teaches only that level, with what to send instead (`replace`), so Off refused on a model that cannot be turned off (Gemini 3.x) omits the parameter for Off and keeps every other level.
5. **The next call goes straight to the safe shape.** `learnedEffortLimit` (`effort-selfheal.ts:201`) feeds `planEffort`. The store is process memory keyed by tenant and bare id, capped at 128 models (`LEARNED_EFFORT_LIMIT_CAP`, `:179`), and **expires after 30 minutes** (`LEARNED_EFFORT_LIMIT_TTL_MS`, `:186`; every new lesson restarts the clock): one refusal can come from one upstream channel or a passing rule, so nothing learned is permanent, and what one tenant's key was refused says nothing about another's.
6. **It is cleared with the job breaker.** `resetModelReliabilityState` (`packages/host/src/job-model-fallback.ts:66`) clears the down circuit and `resetLearnedEffortLimits` (`effort-selfheal.ts:254`); saving Settings (`handlePostSettings`, `packages/host/src/handlers/settings.ts:259`), signing out of the key (`resetGatewayKey`, `:417`) and a tenant reset (`packages/host/src/tenant-reset.ts:315`) call it.

The job-model fallback (`runWithJobModelFallback`, `packages/host/src/job-model-fallback.ts`) is unchanged and still only swaps models on a transport failure; a 400 is `NOT_A_TRANSPORT_FAILURE` (`packages/core/src/models/job-fallback.ts:57`). The self-heal sits below it, so a job that heals never reaches it.

### 5. Ranking keeps newer generations

`FAMILIES` (`preferred.ts:81`) name a brand and a `min` generation, not one generation: GPT 5.6 and newer, Claude 5 and newer, GLM 5 and newer, DeepSeek V4 and newer, every Kimi and MiniMax. `familyGeneration` (`:130`) reads the version off the id (`gpt-6` is [6], `claude-opus-5-5` and `claude-opus-5.5` are [5, 5], `deepseek-v4-1-flash` and `deepseek-v4.1-flash` are [4, 1]; a date suffix is never a minor). `compareWithinFamily` (`:140`) keeps the role first (Luna, Terra, Sol; Sonnet, Opus; flash, pro), so **which model is recommended does not move** while any preferred id is live, and breaks a tie newest first. The recommendation lists were replaced the same day (§ 7). One consequence to know: with none of the ten preferred ids live, `gpt-6-astra` is the family fallback (variant 3, after Luna, Terra and Sol) where it used to be unranked; a live `gpt-6-luna` is one of the ten, and beats `gpt-5.6-luna` inside the Luna role because it is newer.

### 6. Keeping the table honest: `packages/host/eval/models` (dev only)

Two tools, in-process against a desk named by `AGENTFORGE_DATA_DIR`, reading its saved gateway key through the host's own `loadSettings` (`packages/host/src/settings-store.ts:474`). They never call the running `:3000` server, never write the desk, never edit `model-policy.ts`, and never print, log or write the key. Commands and flags: [`packages/host/eval/models/README.md`](../../../packages/host/eval/models/README.md); the recipe: `features/models.md`, "Model policy tools".

- **`catalog-diff`** (`eval:models:diff`, `catalog-diff.ts` → `run-catalog-diff.ts`) reads the desk's saved model cache the way the host does (`listProbedModels`, `packages/host/src/selectable-models.ts:99`) or, with `--refresh`, asks the gateway (`probeOpenAIModels`, the call `refreshModelCache` makes for this gateway) into the report only. For every chat id it prints the policy entry or `UNKNOWN`, the wire and the price; for every list the product ranks by (`CHAT_DEFAULT_PREFERENCES`, `EVERYDAY_MODEL_IDS`, every `JOB_MODE_PREFERENCES.<mode>` with meeting, `JOB_FALLBACK_TAIL`, and the media lists in `MEDIA_MODEL_PREFERENCES`) which ids are `LIVE`, `MISSING`, or live and `UNKNOWN`; and the ids new or gone since the last saved snapshot (`results/catalog-<ts>.json`). **Prices exist:** the gateway's public `GET <origin>/api/pricing` (no key), read by `fetchPricingCatalog` (`packages/core/src/gateway/account.ts:379`, used at `packages/host/src/account-usage.ts:154`) and priced by the same `explainRunUsd` the usage panel uses, at group ratio 1. `/v1/models` itself carries none.
- **`probe`** (`eval:models:probe`, `probe.ts` → `run-probe.ts`, `probe-run.ts`, `probe-call.ts`) sends, per model, a baseline call with no effort parameter and then one call per level (Off, Light, Normal, Deep; Extra and Max with `--extra`), sequential with a pause, a per-call timeout, 32 output tokens and a hard `--max-calls` budget (default 60, retries included). **It does not go through `AiSdkRuntime`:** each request is built raw with the runtime's own body helpers (`probe-request.ts`), so the self-heal is not involved and the policy does not snap or drop a level; that is the point, since an unknown model's profile would otherwise never send Off, Extra or Max. Each call records the HTTP status, the gateway's code and message (one line, 300 characters, key scrubbed), time to first token, total time and the usage the gateway returned (with reasoning tokens where it does), and never a body or header. A refused output budget is adjusted once per kind and retried: a floor ("Expected a value >= 16") raises it, `max_completion_tokens` against `max_tokens` switches the spelling. The trace is `results/probe-<ts>.json`; each model gets a **proposed** `MODEL_POLICY_TABLE` entry (`results/probe-<ts>.snippets.txt`): the wire, the levels the gateway took, `off` as `floor` or `omit` when Off was refused, a `verified` note, and notes on what was not tried, gave no verdict, or disagrees with the table. A human reads it and pastes it, or does not.

## Gotchas

- **Chat sends a level only after the person picks one; the picker still shows Normal.** A fresh browser profile posts `{ content, model }`, so a model the table does not know gets no effort parameter and a known one gets the host's `medium` default, unchanged on the wire. The first time the person touches Thinking (or restores a level they picked before, from `localStorage`) every later send carries `thinking` and `reasoningEffort`. Picking Normal is a pick: it is sent, and an unknown model is then sent `medium`. Before 2026-09-30 the body always carried the level, which made "chosen" true from Chat and the unknown-model profile unreachable from the UI. Not driven in a browser.
- **GPT-6 now gets its level on Responses.** Until the second pass `@ai-sdk/openai` 1.3.24 dropped it (`reasoning` is written only for ids that start with `o` or `gpt-5`, § 3), so a GPT-6 Responses request went out with no effort at all and the policy's "Off becomes low" only ever reached Completions. The runtime adds the block itself now (`applyReasoningToResponsesBody`). **That changes what the flagship does by default:** the host default `medium` is sent as `reasoning: { effort: "medium", summary: "auto" }`, where the gateway used to apply GPT-6's own default. The 20 recorded `gpt-6-astra` bodies were re-recorded for it (the fixture's `rerecorded` note); the other 240 are byte-identical. Not driven against the live gateway: if it answers 400 to `reasoning.effort` for GPT-6 the heal drops the block and learns "takes none" for 30 minutes, which is the pre-change behaviour at the cost of one refused call. A GPT newer than the table (`gpt-7-*`, wire `auto` resolved to Responses) also gets the block now, but only when the person chose a level (its profile is `explicit_only`), capped at Deep.
- **A heal can step to Off.** The step below `low` is `none` when the model allows it, so a refused `low` (the job knob on a quiet family, say) retries with Off. That retry only teaches "send Off in place of Light"; it does not hold Chat at Off. If it turns out too eager, `saferEffortAction` is the place.
- **Classification is text.** The classifier needs the parameter's name and a refusal word in the message. A message that names `thinking` and refuses something else with a word on its list would still be read as a Thinking refusal: one extra request, nothing learned unless the retry succeeds. The refusals it was checked against that it must not take (DeepSeek and Kimi `reasoning_content` errors, Anthropic `thinking.signature`, a temperature rule) are not read that way.
- **The learned map is per tenant and short-lived, not permanent.** It is keyed by tenant and model, holds 30 minutes, and any Settings save clears all of it. The cost is one extra refused request per model per half hour if the gateway keeps refusing. It is not keyed by wire: a limit learned on Responses also caps the same model on Completions.
- **`omni-fast` and the embedding, rerank and audio ids are not policy-known.** They are not chat models. `qwen-mt-*`, `gemini-embedding-*` and `qwen3-vl-*` are known by pattern only because the name rules always treated them as chat.
- **The gateway's `default` alias is unknown to the table**, so a job that resolves to it sends no effort where it used to send `medium`. That is the conservative profile doing its job.
- **`coerceReasoningEffortForModel` is still not on the wire path** (nothing outside its test calls it); the floor happens in the snap. Its behaviour now comes from the policy, and the "cannot go Off" rule lives in one place, for Astra and any GPT 6 id without an entry; for Luna and Sol it answers `none`.
- **Luna and Sol Off is a change on the wire.** Before 2026-09-30 every GPT 6 id floored Off to `low` (`reasoning: {effort: "low", summary: "auto"}`); Luna and Sol now send `reasoning: {effort: "none"}`, with no summary, as gpt-5.6 does. It was seen accepted in the probe's raw requests (both models); the `:3000` drive did not run this tree's runtime, so no request built by it has met the live gateway. The 260 recorded bodies do not include Luna or Sol, so the change is pinned only by `ai-sdk-runtime-responses-reasoning.test.ts`. If the gateway ever answers 400 to `none` for either, the heal drops the block and learns "takes none" for 30 minutes, and the entry is the place to flip back to `floor`.
- **`claude-sonnet-5-5` with Off took 31 s to finish** a 32-token answer in the probe (first token 4.1 s), one sample and unexplained; the other four calls took 2 to 3 s. It is the second Chat default, the second Legal and minutes head and the second outage stand-in.
- **`hy3` has no job knob.** It thinks a little by default (13 to 24 reasoning tokens on a one-word prompt, 0 at Off) and now heads Documents, Finance and Market. If a job on it is slow to the first token, `QUIET_JOB_KNOB` on its entry is the fix; nothing seen says it is needed.
- **`DEFAULT_GATEWAY_VIDEO_MODEL` is still `grok-imagine-video`**, which the gateway does not list. It only answers when the catalogue lists no video id at all (and the `video_generate` tool with no model chosen), so a desk that lists Seedance never reaches it; it was not changed with the list.
- **`gemini-3.7-flash` and `gemini-3.8-flash` are listed, cheaper than `gemini-3.5-flash`, and not probed.** The list keeps 3.5 on the owner's call; both are known to the table through the `gemini` family entry.
- **Line endings.** The tracked tree is CRLF on this desk (`core.autocrlf=true`) and the new files are LF; both commit as LF.

## Why

**Why an unknown model gets a conservative profile rather than the pass-through one.** `[Direct]` the brief for this pass (2026-09-30, Rizky: reliability first): a model from an unknown family used to get `TOKO_COMPLETIONS_EFFORTS`, which passes Extra, Max, Ultra and Off through, and a 400 is not retried (`packages/core/src/runtime/retry.ts:73`). `[Supported]` `docs/internal/gateway-model-selection.md` section 3 shows the families disagree about which of those levels exist (GPT-6 answers `none` with HTTP 400; Gemini 3 cannot be turned off; Claude Fable cannot be either). **Confidence: high for the mechanism; the exact conservative set (low, medium, high) is a judgement.**

**Why the job knob is now part of the plan.** `[Direct]` `packages/core/src/models/job-thinking.ts` and the 2026-09-15 drive it records: `reasoning_effort: "low"` answers 200 where `thinking: {type: "disabled"}` answers 400. Keeping the knob a separate overwrite after the plan would let it rewrite a level the heal had just stepped down. **Confidence: high.**

**Why a lesson is as narrow as its refusal, and expires.** `[Inferred]` from the review of this change: teaching "drop everything" or "hold at Off" from one refused Off or one refused Light would have turned a Gemini 3 Off click, which `docs/internal/gateway-model-selection.md` says the model cannot do, into a process-wide loss of that model's Thinking levels, and one upstream channel's refusal would have followed every tenant until restart. **Confidence: medium; the 30-minute hold is a judgement modelled on the job breaker's five minutes.**

**Why the runtime adds the Responses `reasoning` block itself and does not upgrade the SDK.** `[Direct]` the brief for the second pass (2026-09-30, Rizky: reliability first): GPT-6 never received the level the picker showed, and the fix should be the smallest robust seam without upgrading the AI SDK. `[Supported]` `getResponsesModelConfig` in `@ai-sdk/openai` 1.3.24 keys on `startsWith("o") || startsWith("gpt-5")`, so any id outside those prefixes is a non-reasoning model to the SDK whatever the policy says; the body wrapper already exists for Completions, so extending it to `/responses` keeps one place that writes a level onto the wire and lets the heal and the Off floor work unchanged. **Confidence: high for the mechanism (42 runtime tests, the recorded bodies); the effect on the live gateway is not driven.**

**Why the probe sends raw requests instead of running the runtime with the heal off.** `[Inferred]` from the shape of the policy: an unknown model's profile snaps Extra, Max and Ultra to Deep and never sends Off, so a probe through the runtime could never see what the gateway does with them, and the heal would repair the very refusals the probe exists to record. Building each body with the runtime's own helpers keeps the shape faithful and takes the snapping out. **Confidence: medium; the bodies are the runtime's, the headers and stream reading are the tool's own and have only met a loopback fake.**

**Why the lists follow price and speed, and not a quality comparison.** `[Direct]` the owner's brief (2026-09-30): the recommendation was delegated with an explicit order, Chat default `gpt-6-luna` as the cheapest and fast, and the per-mode lists as given. `[Supported]` the gateway's price list ($0.10 / $0.50 per 1M for `gpt-6-luna`, $2 / $10 for `gpt-6-sol` and `claude-sonnet-5-5`) and the probe (first token 1.3 to 2.3 s for Luna, DeepSeek V4.1 Flash and `hy3`; 5 to 7 s for Astra). `[Inferred]` that Documents, Finance, Market, Legal and the minutes run well on the new heads: only reachability, Thinking levels and latency were measured, no answer was compared. **Confidence: high that each id answers and takes the levels the table says; low on the quality of any head relative to the one it replaced.**

**Why Luna and Sol get `none` and Astra does not.** `[Direct]` the probe of 2026-09-30, raw Responses requests: `none` answered 200 for `gpt-6-luna` and `gpt-6-sol` and 400 (`Unsupported value: 'none'`) for `gpt-6-astra`. `[Supported]` `docs/internal/gateway-model-selection.md` § 3 recorded the 400 for "GPT-6", from the one GPT 6 id that existed on 2026-09-13. **Confidence: high for one call each, no repeat.**
