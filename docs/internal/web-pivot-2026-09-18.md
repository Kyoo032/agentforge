# Direction change: DPSBuddy becomes a hosted web app (2026-09-18)

**Status:** decided by Kyo, 2026-09-18. Verified against `main` at `986f113`.

This page is the record. Every other doc that mentions the product target links here instead of restating the decision.

## Decision

DPSBuddy becomes a **hosted, multi-user web app (SaaS)**. Kyo runs it on a server. Users open it in a browser and sign in through the Toko Token portal — device-code today, a browser login for the web app. Data is per tenant on the server. The 20-seat paywall and the entitlement gate live server-side.

The Windows / macOS Electron desktop app is **frozen at 0.14.27**: maintenance-only, no new features, no new cuts unless Kyo asks. The gateway (`api.tokotokenai.com`) stays the model backend; **gateway-first is unchanged**.

## What is frozen

- **Desktop app at 0.14.27.** The Electron shell still exists, still builds, and 0.14.27 is published. It receives maintenance fixes only. It is frozen, not removed.
- **The DPSBuddy releases repo** (`Kyoo032/DPSBuddy`) and `pnpm desktop:release` are **desktop-maintenance-only**. Nothing about the hosted web app is published there.
- **The pack skill and the pack / release routes** still work as written and stay as-is. `docs/internal/maps/desktop-pack-routes.md` documents a frozen route.
- **The version scheme.** `0.14.2x` continues, for desktop maintenance cuts only. No `0.15` until Kyo says so. Web deploys are tracked by commit sha in the deploy log below, not by a version number.

## What changes in the rules

- **Product target.** "Web target" replaces "Desktop target". The product is served by the existing Express host (`apps/web/server.ts:7-54`) with the Vite renderer, over HTTPS behind a reverse proxy, on Kyo's server.
- **Ownership model.** "Single owner on the machine" becomes: **one server, many tenants; every row belongs to a tenant; the host enforces tenancy, the renderer displays.**
- **The HTTP server is the product.** "Local process only / packaged Electron has no HTTP server" no longer describes the target. The loopback-only Origin allowlist in `packages/host/src/local-request.ts:75-84` (`isAllowedMutatingApiRequest`, wired at `packages/host/src/http-adapter.ts:188`) must become a **trusted-origin allowlist plus CSRF protection** before the web app is exposed. Until that lands, the host must still bind loopback and sit behind the proxy.
- **Secrets.** The wrap key comes from `AGENTFORGE_SECRETS_KEY` (env / secret manager) on the server — never from a file in the repo, never from keytar. `packages/db/src/vault-key.ts:37-51` already reads the env first. Per-tenant gateway keys stay in the AES-256-GCM envelope (`packages/core/src/crypto/envelope.ts`).
- **Data.** SQLite (`packages/db/src/vault-key.ts:21-35`) is fine for the first hosted deployment, which is a single server. Postgres for tenancy is an **open decision, not a rule** — do not write "use Postgres". The old rule "do not set `DATABASE_URL` to Postgres" becomes **"SQLite until the tenancy design says otherwise"**.
- **Login.** Portal login stays the only account concept. For the web app it becomes a **browser session issued by the portal**, not `device.json` / `session.enc` in a local data dir. The desktop-side seat-gate spec on the cloud branch is stale.
- **Shipping.** "Nothing counts as shipped until packed and installed" becomes **"nothing counts as shipped until deployed to the hosted environment and driven there"**. The packed-and-installed rule survives for desktop maintenance only.
- **Versioning.** The `0.14.2x` scheme continues for desktop maintenance cuts only. Web deploys are tracked by commit sha in the deploy log below. No `0.15` until Kyo says so (unchanged).
- **Unchanged:** the webdev `:3000` rules (isolated instance, drive everything there, never a second port, hot reload), and the locale, tests, kernel-schema, modality fail-closed and secrets-in-git rules.

## Open decisions

None of these are resolved. They are listed so nobody invents an answer in a PR.

1. **Tenancy model in the schema** — a tenant column on every table vs a database per tenant, and SQLite vs Postgres. — Owner: Kyo — Status: open
2. **Browser login flow with the portal** — cookie session vs bearer, refresh, sign-out. — Owner: Kyo — Status: open
3. **Trusted-origin allowlist + CSRF for mutating `/api`.** — Owner: Kyo — Status: open
4. **Hosting** — Tencent Cloud CVM in Jakarta (Kyo, 2026-09-18); proxy, TLS, backups and the deploy command are in `webapp-deploy/`; storage placement in [`web-data-placement-tencent.md`](web-data-placement-tencent.md); the security requirements in [`web-security-spec.md`](web-security-spec.md). — Owner: Kyo — Status: decided (CVM); placement proposed
5. **Media and job outputs storage per tenant** — today they are files on disk under the data dir; proposed: CBS disk until Phase 6, then COS with a per-tenant prefix ([`web-data-placement-tencent.md`](web-data-placement-tencent.md) §3). — Owner: Kyo — Status: proposed
6. **Component installer on a server** — native modules such as `better-sqlite3` and anydoc: who installs them, and when. — Owner: Kyo — Status: open
7. **What happens to Electron-only surfaces** — Start over wipe, `host-status.json`, and the IPC bridge (`apps/web/lib/desktop-bridge.ts`). — Owner: Kyo — Status: open
8. **Pricing model: two plans** (Kyo, 2026-09-18). **Personal** is a subscription per user with a monthly token allowance included. **Enterprise** is seat-based per organisation, the seat rule from `docs/internal/portal/` (20-seat paywall, seat = active member). Both are a tenant plan row (`active` / `past_due` / `cancelled`, set by the billing provider's webhook) that the host checks before it calls the gateway; Personal adds a per-tenant usage quota, Enterprise adds the seat counter. The per-run usage records and USD estimates in `packages/host/src/account-usage.ts` are the metering base. Prototype of the account and plan screens comes first (design, then webdev). Still open: who holds the gateway key on Personal (operator key with quotas is the working assumption), tier sizes, overage behaviour (block vs meter), and the billing provider (Xendit / Paddle / Stripe by selling entity). — Owner: Kyo — Status: decided (two plans); details open

## Architecture today

Verified 2026-09-18 at `986f113`. These are facts about the tree as it stands, not a target design.

- **Webdev / prod server:** `apps/web/server.ts:7-54`. Express; Vite middleware in dev; static `dist` plus SPA fallback in prod. Binds `127.0.0.1`. Port from `PORT`, default 3000.
- **Renderer transport:** `apps/web/lib/api-client.ts:97-98` uses `fetch` when not Electron; Electron goes through `window.agentforge.invoke` via `apps/web/lib/desktop-bridge.ts`.
- **Origin check:** `packages/host/src/local-request.ts:75-84` (`isAllowedMutatingApiRequest`), wired at `packages/host/src/http-adapter.ts:188`.
- **Wrap key:** `packages/db/src/vault-key.ts:37-51` — env `AGENTFORGE_SECRETS_KEY`, else a `.master-key` file in `localDataDir`. The Electron keytar override lives in `apps/desktop/main.cjs:265-294`.
- **SQLite path:** `packages/db/src/vault-key.ts:6-35`.
- **Build and run:** `pnpm build` in `apps/web` is `vite build` to `apps/web/dist`; the prod run is `NODE_ENV=production tsx server.ts`. **No Dockerfile for the web app exists yet.**
