# Direction change: DPSBuddy becomes a hosted web app (2026-09-18)

**Status:** decided by Rizky, 2026-09-18. Verified against `main` at `986f113`.

This page is the record. Every other doc that mentions the product target links here instead of restating the decision.

## Decision

DPSBuddy becomes a **hosted, multi-user web app (SaaS)**. Rizky runs it on a server. Users open it in a browser and sign in through the Toko Token portal — device-code today, a browser login for the web app. Data is per tenant on the server. The 20-seat paywall and the entitlement gate live server-side.

**Revised 2026-09-23.** The product did not end up as web-only. Rizky split DPSBuddy into **two products** — **Personal** (the Mac/Windows app, released `0.15.0` on 2026-09-23, under active development again) and **Enterprise** (the hosted multi-user web app) — and both continue. Read the sections below as the record of the 2026-09-18 pivot; where they say the desktop is frozen or that the web app is the only product, the 2026-09-23 re-scope at the end of this file supersedes them.

## What was frozen on 2026-09-18 (superseded 2026-09-23)

- **Desktop app at 0.14.27 — no longer frozen.** It was maintenance-only from 2026-09-18 until 2026-09-23; it is under active development again and `0.15.0` shipped.
- **The DPSBuddy releases repo** (`Kyoo032/DPSBuddy`) and `pnpm desktop:release` are the **Personal** app's release route. Nothing about the hosted web app is published there. Since 2026-09-23 the hosted web app has its own public release repo, `Kyoo032/DPSBuddy-Ent` — see **Three repos (2026-09-23)** below.
- **The pack skill and the pack / release routes** work as written and serve the Personal app.
- **The version scheme.** `0.14.2x` was scoped to desktop *maintenance* cuts while the desktop was frozen. `0.15.0` is a product release and takes the next minor; the next maintenance cut would be `0.15.1`. Web deploys are tracked by commit sha in the deploy log below, not by a version number.

## What changes in the rules

- **Product target.** "Web target" replaces "Desktop target". The product is served by the existing Express host (`apps/web/server.ts:7-54`) with the Vite renderer, over HTTPS behind a reverse proxy, on Rizky's server.
- **Ownership model.** "Single owner on the machine" becomes: **one server, many tenants; every row belongs to a tenant; the host enforces tenancy, the renderer displays.**
- **The HTTP server is the product.** "Local process only / packaged Electron has no HTTP server" no longer describes the target. The loopback-only Origin allowlist in `packages/host/src/local-request.ts:80-89` (`isAllowedMutatingApiRequest`, wired at `packages/host/src/http-adapter.ts:560`) became a **trusted-origin allowlist plus CSRF protection** in Phase 1, landed in [PR #56](https://github.com/Kyoo032/agentforge/pull/56) (commit `6ae177a`): `isAllowedWebOrigin` / `isAllowedWebHostHeader` (`packages/host/src/local-request.ts:99,113`, chosen at `http-adapter.ts:529`) and the CSRF token in `packages/host/src/csrf.ts`, both reached only when `isServerMode()` (`packages/core/src/server-mode.ts`) is on. The loopback rule is unchanged for desktop and webdev. The host still binds loopback and sits behind the proxy, now by deployment choice rather than because the check is missing.
- **Secrets.** The wrap key comes from `AGENTFORGE_SECRETS_KEY` (env / secret manager) on the server — never from a file in the repo, never from keytar. `packages/db/src/vault-key.ts:37-51` already reads the env first. Per-tenant gateway keys stay in the AES-256-GCM envelope (`packages/core/src/crypto/envelope.ts`).
- **Data.** SQLite (`packages/db/src/vault-key.ts:21-35`) is fine for the first hosted deployment, which is a single server. Postgres for tenancy is an **open decision, not a rule** — do not write "use Postgres". The old rule "do not set `DATABASE_URL` to Postgres" becomes **"SQLite until the tenancy design says otherwise"**.
- **Login.** Portal login stays the only account concept. For the web app it becomes a **browser session issued by the portal**, not `device.json` / `session.enc` in a local data dir. The desktop-side seat-gate spec on the cloud branch is stale.
- **Shipping.** "Nothing counts as shipped until packed and installed" becomes **"nothing counts as shipped until deployed to the hosted environment and driven there"** — that rule applies to Enterprise. For **Personal** it is still "packed, installed and driven on the packaged app" (`doctor --desktop`), which is what the 0.15.0 release did on Windows.
- **Versioning.** `0.15.0` is the current Personal cut (released 2026-09-23). Semver continues; the next maintenance cut would be `0.15.1`. Web deploys are tracked by commit sha in the deploy log below. **The old "No `0.15` until Rizky says so" rule is spent** — he said so on 2026-09-23.
- **Unchanged:** the webdev `:3000` rules (isolated instance, drive everything there, never a second port, hot reload), and the locale, tests, kernel-schema, modality fail-closed and secrets-in-git rules.

## Open decisions

Listed so nobody invents an answer in a PR. Each carries its own status; a resolved one stays here with a pointer to where it landed.

1. **Tenancy model in the schema** — a tenant column on every table vs a database per tenant, and SQLite vs Postgres. — Owner: Rizky — Status: open
2. **Browser login flow with the portal** — cookie session vs bearer, refresh, sign-out. — Owner: Rizky — Status: open
3. **Trusted-origin allowlist + CSRF for mutating `/api`.** — Owner: Rizky — **Status: landed.** Shipped as Phase 1 in [PR #56](https://github.com/Kyoo032/agentforge/pull/56) (commit `6ae177a`): a config-driven origin and Host allowlist (`packages/host/src/local-request.ts:99,113`, chosen at `http-adapter.ts:529`), a double-submit CSRF token (`packages/host/src/csrf.ts`) minted on first GET and required on every mutating `/api` call — bare randomness today, **not** bound to a session; `csrf.ts:14-17` records binding it to the portal session as a follow-up, and the Phase 3 spec carries it at § 5 (`auth` row), and the existing `x-agentforge-transport` header, all behind `isServerMode()` (`packages/core/src/server-mode.ts`). See `web-migration-plan.md` § Phase 1.
4. **Hosting** — Tencent Cloud CVM in Jakarta (Rizky, 2026-09-18); proxy, TLS, backups and the deploy command are in `webapp-deploy/`; storage placement in [`web-data-placement-tencent.md`](web-data-placement-tencent.md); the security requirements in [`web-security-spec.md`](web-security-spec.md). — Owner: Rizky — Status: decided (CVM); placement proposed
5. **Media and job outputs storage per tenant** — today they are files on disk under the data dir; proposed: CBS disk until Phase 6, then COS with a per-tenant prefix ([`web-data-placement-tencent.md`](web-data-placement-tencent.md) §3). — Owner: Rizky — Status: proposed
6. **Component installer on a server** — native modules such as `better-sqlite3` and anydoc: who installs them, and when. — Owner: Rizky — Status: open
7. **What happens to Electron-only surfaces** — Start over wipe, `host-status.json`, and the IPC bridge (`apps/web/lib/desktop-bridge.ts`). — Owner: Rizky — Status: open

8. **Pricing model: two plans** (Rizky, 2026-09-18). **Personal** is a subscription per user with a monthly token allowance included. **Enterprise** is seat-based per organisation, the seat rule from `docs/internal/portal/` (20-seat paywall, seat = active member). Both are a tenant plan row (`active` / `past_due` / `cancelled`, set by the billing provider's webhook) that the host checks before it calls the gateway; Personal adds a per-tenant usage quota, Enterprise adds the seat counter. The per-run usage records and USD estimates in `packages/host/src/account-usage.ts` are the metering base. Prototype of the account and plan screens comes first (design, then webdev). Still open: who holds the gateway key on Personal (operator key with quotas is the working assumption), tier sizes, overage behaviour (block vs meter), and the billing provider (Xendit / Paddle / Stripe by selling entity). — Owner: Rizky — Status: decided (two plans); details open

## Three repos (2026-09-23)

**Status:** decided by Rizky, 2026-09-23.

- **`Kyoo032/agentforge` (private)** stays the single source repo for both products: code, docs, branches, webdev, packing, verification. How work is done does not change.
- **`Kyoo032/DPSBuddy` (public)** stays the Personal release repo: installers and the updater feed, published by `pnpm desktop:release`.
- **`Kyoo032/DPSBuddy-Ent` (public, new)** is the Enterprise **deploy-bundle and release repo**, refined by Rizky later the same day from "release notes only". It stands to agentforge the way `Kyoo032/DPSBuddy` does: built and pushed from agentforge by a script, `node scripts/release-web.mjs`. Its `main` holds the README, the LICENSE and the current bundle: `compose.yml` pinned to the private image `ghcr.io/kyoo032/dpsbuddy-ent:<tag>`, `.env.example` with the names the hosted app refuses to boot without, a five-step `DEPLOY.md`, and the `Caddyfile` the proxy mounts. Each release is a `Release <tag>` commit plus a GitHub Release whose notes come from `docs/public/ent-YYYY.MM.DD-notes.md` and end with `Source: agentforge@<sha>` and `Image: <image>`.

**Why one source repo.** Both products are built from the same `apps/web`, `packages/core` and `packages/host`. Splitting the source would mean two copies of the renderer and the host, and every UI or host fix landing twice.

**Why two release repos.** Customers of each product see only their own releases. A Personal user reading `Kyoo032/DPSBuddy` never sees Enterprise notes, and an Enterprise customer reading `Kyoo032/DPSBuddy-Ent` never sees installers or updater feeds.

**Rules shared by both public repos.** Never source, never `docs/internal/`, never AI/agent marks. Releases are authored as Rizky with plain messages and no trailers, notes come from `docs/public/`, and a script publishes them — never by hand, never with a `git push` from agentforge.

**The only local checkout is `agentforge`.** `Kyoo032/DPSBuddy` and `Kyoo032/DPSBuddy-Ent` are written only by their release scripts. No second clone is kept on disk: `release-web.mjs` clones DPSBuddy-Ent into a temp dir under `%TEMP%`, writes the bundle, pushes, and deletes the dir before it exits. The same temp dir holds the `git archive <sha>` the image is built from.

**What the script does, in order.** Preflight (clean tree unless `--allow-dirty`; sha resolves; notes exist; no banned mark in the notes, the body or any bundle file). Then image: `git archive <sha>`, `docker build -f webapp-deploy/Dockerfile -t ghcr.io/kyoo032/dpsbuddy-ent:<tag> .` in the extracted tree, and `docker push` (`--skip-image` skips only this step). Then bundle: clone, write, commit `Release <tag>`, push `main`, delete. Last, `gh release create <tag> --notes-file` and `gh release view`. `--dry-run` runs none of docker, gh, tar, or any git that writes; it reads this repo (`status`, `rev-parse`, `show <sha>:webapp-deploy/Caddyfile`) and prints the plan. The first dry run (`--tag ent-2026.09.23 --sha 0b73a68 --dry-run --allow-dirty`, 2026-09-23) passed with a placeholder notes file.

**What the image is, and what it must not become (finding, 2026-09-23).** The smallest artifact that runs the hosted app without shipping TypeScript is not built yet. `webapp-deploy/Dockerfile` copies the whole context in its build stage (`:53`) and the whole build tree into the runtime stage (`:103`), because the host runs `tsx server.ts` against package sources (`:8-12`, `:153`). So the image holds every `.ts` file in `apps/` and `packages/`, `apps/portal`, `scripts/`, `packages/host/eval/` and the root `AGENTS.md`. `docs/` is excluded by `Dockerfile.dockerignore:44`, so `docs/internal/` does not ship. Separately, that ignore file's `.env`, `.env.local` and `data` match only at the context root, so a build from this desk's checkout would have baked in `.webdev-data-design/` (a `.master-key`, `settings.enc` and SQLite file) and `apps/web/.env.local` (provider keys). Two consequences, both recorded as SR-49 in [`security-register.md`](security-register.md):
- The release script builds only from `git archive <sha>`, so untracked files cannot reach the image. The ghcr package stays **private**, and the server pulls it with a read-only packages token.
- The fix belongs to the Dockerfile and was deliberately not made in this pass. Anchor the ignore patterns everywhere (`**/.env*` except `.env.example`, `.webdev-data*`, `**/data/`, eval results). Make the runtime stage copy only `apps/web/dist`, an esbuilt host bundle (the way `apps/desktop/scripts/stage-renderer.mjs:23-31` builds `host.cjs`), `packages/db/drizzle`, and the production native modules. That drops the source, `tsx` and the dev dependencies, and it is the condition for ever making the image public.

`webapp-deploy/scripts/deploy.sh` still builds on the Jakarta box from a `git pull` checkout. Moving that box to `docker compose pull` of a released bundle is the next deploy-path decision; until it is made, both paths exist and the deploy log says which one ran.

**Tag.** Web deploys still carry no semver. The DPSBuddy-Ent tag is `ent-YYYY.MM.DD`, with `.N` for a second release the same day, and every release body names the agentforge commit sha. Rizky has not confirmed the tag scheme; ent-CalVer is the working default.

## Architecture today

Verified 2026-09-18 at `986f113`. These are facts about the tree as it stands, not a target design.

- **Webdev / prod server:** `apps/web/server.ts:7-54`. Express; Vite middleware in dev; static `dist` plus SPA fallback in prod. Binds `127.0.0.1`. Port from `PORT`, default 3000.
- **Renderer transport:** `apps/web/lib/api-client.ts:97-98` uses `fetch` when not Electron; Electron goes through `window.agentforge.invoke` via `apps/web/lib/desktop-bridge.ts`.
- **Origin check:** `packages/host/src/local-request.ts:80-89` (`isAllowedMutatingApiRequest`), wired at `packages/host/src/http-adapter.ts:560`. **Superseded in server mode by Phase 1** (PR #56): `isAllowedWebOrigin` / `isAllowedWebHostHeader` plus the CSRF check in `packages/host/src/csrf.ts`. `isAllowedMutatingApiRequest` is still the desktop and webdev path.
- **Wrap key:** `packages/db/src/vault-key.ts:37-51` — env `AGENTFORGE_SECRETS_KEY`, else a `.master-key` file in `localDataDir`. The Electron keytar override lives in `apps/desktop/main.cjs:265-294`.
- **SQLite path:** `packages/db/src/vault-key.ts:6-35`.
- **Build and run:** `pnpm build` in `apps/web` is `vite build` to `apps/web/dist`; the prod run is `NODE_ENV=production tsx server.ts`. **No Dockerfile for the web app exists yet.**
