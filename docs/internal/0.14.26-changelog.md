## Stream watchdog: quiet reasoning models no longer time out — 2026-09-15

**Symptom:** Finance and Documents answered `500 internal_error` "No stream events from deepseek-v4-flash for 60s after it started (timeout)" on the default job model while the model was working; the same body on `gpt-5.6-luna` returned a brief, and short `/api/v1/finance/parse` calls passed, which is why it read as a model fault. Two defects in our own code.

**D1:** `AiSdkRuntime.consume` fed the watchdog from every `fullStream` part, and the AI SDK enqueues `step-start` on the provider's first chunk (`ai/dist/index.mjs`, `stepFirstChunk`) while `@ai-sdk/openai` emits `response-metadata` on the gateway's very first SSE frame — so half a second in, before any token, the 120 s first-token budget was swapped for the 60 s idle one (the reported error is the *idle* wording, which proves a part had already landed).

**D2:** the resolved Finance/Documents/Market default is `deepseek-v4-flash` (the `hy3` first choice is not in this gateway's catalog), and DeepSeek V4 thinks on by default (`docs/internal/gateway-model-selection.md`); its thinking streams as `delta.reasoning_content`, which AI SDK 4 drops (the same gap `packages/core/src/runtime/minimax-compat.ts` was written for), so nothing at all reached the watchdog for the ~50 s the model spent drafting.

**Fix in core, no model default changed:** `QUIET_REASONING_FAMILY` (`deepseek-v4`, `glm-5.3`, `kimi-k3`, `qwen3.8-max`) now counts as a reasoning model in `packages/core/src/runtime/stream-watchdog.ts`, so these get the existing 240 s / 180 s floors; `StreamWatchdogState` gained `streaming`, and until the model produces output the deadline is `max(start + ttfb, lastEvent + idle)` — an output-less frame can only push the wait out, never shorten it; `armStreamWatchdog` gained `touchOutput()`, which `packages/core/src/runtime/ai-sdk-runtime.ts` calls only for parts `mapStreamPart` recognises.

**Chat had the same disease one layer up:** `packages/host/src/runs.ts` armed a one-shot `setTimeout(limits.ttfbMs)` at run start and never rearmed it, a cap on the whole run wearing the first-token message — a healthy chat run streaming at 21 s and 79 s was killed at 121 s with "Tidak ada token pertama … setelah 120 detik". It now uses `armRunStallGuard` / `isRunOutputEvent` (`packages/host/src/run-stall.ts`), rearmed from `onEvent` with the model's own reasoning-aware limits and the same bilingual copy.

**Measured** on the 3100 desk before the fix: the given body failed at ~66.7 s wall, the same body passed once at 52.9 s (49.4 s of it silent in `drafting`), a minimal prompt on the same model finished in ~21 s, and a chat run showed 21.2 s to the first delta then a 57.05 s silent gap mid-stream.

**Driven 2026-09-15 after a restart of the webdev desk**, same Finance body on `deepseek-v4-flash`: API 3 attempts → 500 at 241 s ("No first token after 240s"), 200 at 75 s, 500 at 240 s; UI 2 runs → one 240 s failure, then 38 s — the longer budget rescues every attempt that speaks at all, and about half still say nothing for the full 240 s. So the product half of D2 went in too: a job run asks the always-thinking families for their lowest effort.

**First attempt was wrong and the desk caught it:** sending DeepSeek's documented `thinking: {"type":"disabled"}` made every Finance call on `deepseek-v4-flash` and `deepseek-v4-pro` fail with HTTP 400 in 2-4 s, 5/5, the `/finance/parse` call included — this gateway's passthrough rejects vendor-only fields — while `glm-5.3-flash` with `reasoning_effort: "low"` alone returned 200 in 12 s and Chat on the same model was unaffected. Every family now sends `{"reasoning_effort":"low"}` and nothing else (Qwen's `enable_thinking: false` dropped for the same reason), replacing the generic `reasoning_effort: "medium"` the chat ladder used to put on a studio's request; `reasoning_effort` is the proven field because Chat sends it to these ids on every turn.

Jobs need no hidden reasoning pass: Finance computes every metric in code and the model only writes narrative over it. Pure mapping in `packages/core/src/models/job-thinking.ts` (`jobThinkingExtras` / `applyJobThinking`), applied to the chat-completions body in `ai-sdk-runtime.ts` only when `execute` carries the new `jobMode`; Chat never sets it and its body is unchanged byte for byte. Every studio names its mode at its `collectJobAssistantText` call (finance, documents, presentations, research, data, market, legal), and so do Enhance prompt and the knowledge map. `EFFECTIVE_JOB_MODEL` in `models/mode-defaults.ts` now states in one place that `hy3` is absent from this gateway's catalog so `deepseek-v4-flash` is the real job default — nothing reordered yet.

That 400 also surfaced in Indonesian on an English desk, so a gateway 400 / 401 / 403 / 429 / 5xx now reads in the app locale (`packages/core/src/gateway-http-copy.ts`, `gatewayHttpFailure`) with the status code kept in the headline and the upstream sentence only in the log; 402, 404 and the rest still pass through verbatim because `isMissingWireEndpoint` classifies on them.

## Second security pass — gate durability, loopback CSRF, Electron shell — 2026-09-15 (later)

The whole-codebase audit's first surface, written up in [`blockers-2026-09-15.md`](blockers-2026-09-15.md) §3.2 (a) and (c).

**Host:** `saveGateState` no longer throws — a data dir it cannot write costs a cached verdict and nothing more, it warns through `redactSecrets` and returns `{ state, persisted }`, and `runGatewayCheck` reports `status: "error"` with `GATEWAY_VERDICT_UNWRITABLE_MESSAGE` rather than a confident verdict that disk never kept; `allowed` is untouched, because an unwritable file is not a rejected key. The post-save refresh in `handleSaveSettings` is wrapped in its own try/catch for the same reason: before this, an EACCES/ENOSPC at `gateway-gate.json` told the owner "saving your key failed" for a key that *was* saved. `handleCancelReset` uses `recursive: true` so a directory at the marker path cannot 500 a cancel. Mutating `/api` now also requires a loopback `Host` (a missing Host is refused, unlike a missing Origin — HTTP/1.1 makes it mandatory and `pathnameOf` would otherwise default it to `127.0.0.1`), and `POST`/`DELETE /api/v1/settings/reset` additionally require an `x-agentforge-transport` header, which `apiFetch` now stamps on every mutating renderer call in one place — a cross-site HTML form can POST to `127.0.0.1:3000` but cannot set a custom header. GETs are byte-for-byte unchanged. ## Chat model picker fix — 2026-09-15

**What:** in Chat the model picker opened but nothing could be selected — the list appeared as a thin sliver inside the composer toolbar row, options were invisible and un-clickable, so the model never changed. Keyboard (Ctrl/Cmd+K, arrows, Enter) still worked, which is why it slipped through.

**Root cause:** the single-row composer toolbar wraps its left group in `flex min-w-0 flex-1 items-center gap-2 overflow-hidden` (`apps/web/components/chat-composer.tsx:390`) so the trigger row cannot push the Send button out. `ModelPicker` rendered its panel as `absolute bottom-full … z-50` inside that group, and the group is an overflow ancestor of the panel's containing block, so the panel was **clipped to the 32px toolbar row**. `z-50` does not escape a clip. `elementsFromPoint` over an option returned `message-list`, i.e. clicks landed on the transcript behind the composer. Nothing was wrong with the wiring — `onChange` → `handleModelChange` → `pickChatModel` / `chat-model-pref.ts` and the `/api/v1/models` payload were all fine, and the locale sweep of `model-picker.tsx` is not implicated.

**Fix:** `apps/web/components/model-picker.tsx` now portals the option list to `document.body` (`createPortal`, `fixed z-[80]`, `data-testid="model-picker-panel"`) and positions it against the trigger with the new `apps/web/lib/picker-panel.ts` (`placePickerPanel` / `viewportBounds`): opens upward by default, flips below when there is no room above, clamps left/width to the viewport gutters, caps height at 344px (the old `max-h-72` list plus the search row) and re-places on resize and scroll — the same pattern `chat-context-chip.tsx` and `workspace-switcher.tsx` already use. The toolbar's `overflow-hidden` is left alone: at ≤700px the group genuinely does clip (scrollWidth 195 vs clientWidth 109), so it is load-bearing. No copy changed, so no en/id catalog work.

**Tests:** `apps/web/lib/picker-panel.test.ts` — five placement cases (above, flip below, narrow-pane clamp, right-edge clamp, minimum height) plus two source guards that the picker still portals (`createPortal` + `placePickerPanel`, no `absolute bottom-full`) and that the toolbar still clips.
