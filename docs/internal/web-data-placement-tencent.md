# Where the data lives: DPSBuddy on Tencent Cloud CVM

**Status:** design, decided by Kyo on 2026-09-18 that the host is a Tencent Cloud CVM. Storage placement below is the proposal; each row says which migration phase makes it real. Companion: [`web-security-spec.md`](web-security-spec.md), [`web-migration-plan.md`](web-migration-plan.md), [`web-pivot-2026-09-18.md`](web-pivot-2026-09-18.md), [`../../webapp-deploy/README.md`](../../webapp-deploy/README.md).

Product names are Tencent Cloud's as of September 2026; check the console for current instance families and prices before ordering.

## 1. Region and residency

- **Region: Jakarta (`ap-jakarta`)**, one availability zone to start. Users and the selling entity are Indonesian; Indonesia's personal data law (UU PDP 27/2022) is simplest to meet when personal data stays in-country. Singapore (`ap-singapore`) is the backup-copy region only.
- Everything below sits in **one VPC** with a private subnet for data services and a public subnet holding only the load balancer. Nothing that stores data has a public IP.

## 2. What the app stores today

The host writes one data root (`AGENTFORGE_DATA_DIR`, `/data` in the container). Its entries are the `HOST_RESET_ENTRIES` list in `packages/host/src/handlers/settings.ts:274-296`, plus the SQLite file from `packages/db/src/vault-key.ts:21-35`:

| Entry | What it is | Sensitivity |
|---|---|---|
| `agentforge.sqlite` (+ `-wal`, `-shm`) | threads, runs, workspaces, usage rows, knowledge, matters | high: personal data, tenant work |
| `settings.enc` | per-workspace secrets, AES-256-GCM envelope (`packages/core/src/crypto/envelope.ts`); gateway keys live here | critical |
| `.master-key` | file fallback for the wrap key; must not exist on the server (Phase 1 makes `AGENTFORGE_SECRETS_KEY` mandatory) | critical |
| `settings.json` | legacy plaintext settings from before the envelope; must be empty or absent on the server, and the reset list still names it | medium |
| `gateway-gate.json`, `desk-usage.json`, `workspace-id.txt`, `models*-cache.json` | per-install state that becomes per-tenant rows (Phases 3 and 5) | low to medium |
| `media/<orgId>/…` | generated images, videos, uploads (`packages/host/src/media.ts:85-89`) | high: tenant content |
| `edit/`, `datasets/`, `legal/` | job scratch and outputs (`edit/ffmpeg/paths.ts:42-44`, `datasets.ts:315-317`, `legal/store.ts:306`) | high |
| `components/`, `logs/` | downloaded native components and the installer's diagnostics | none: re-downloadable |

## 3. Placement, by phase

| Data | Phase 0-2 (single owner, then sessions) | Phase 3+ (tenancy) | Tencent service |
|---|---|---|---|
| Relational data | SQLite on a **dedicated CBS disk** mounted at `/data`, separate from the system disk; WAL mode stays on | **TencentDB for PostgreSQL**, single-AZ to start, private subnet, automatic daily backups plus 7-day PITR; tenant column on every table per the migration plan | CBS Premium SSD (Phase 0), TencentDB for PostgreSQL (Phase 3) |
| Tenant secrets (`settings.enc`) | Stays an envelope file on `/data` | Envelope rows in Postgres, one per tenant workspace; same cipher, same wrap key | Postgres |
| Wrap key (`AGENTFORGE_SECRETS_KEY`) | Held in **Secrets Manager (SSM)**, fetched at container start by `deploy.sh`, injected as env, never written to disk in the repo or the image | Same; rotated by re-wrapping envelopes (Phase 4 task) | SSM, with the key material generated by KMS |
| Media, uploads, job outputs | On the `/data` CBS disk | **COS**, one private bucket, prefix `tenants/<tenantId>/…`, server-side encryption SSE-KMS, delivered through short-lived pre-signed URLs; the storage interface in Phase 6 hides the switch from handlers | COS |
| Backups | Nightly CBS snapshot (7 kept) plus an hourly `backup.sh` run that ships the SQLite `.backup` copy and a tar of `/data` to a **separate COS bucket** | Postgres managed backups plus a nightly logical dump to the backup bucket; COS bucket versioning on, lifecycle to ARCHIVE after 30 days, delete after 365 | CBS snapshots, COS |
| Backup copy off-region | Cross-region replication of the backup bucket to Singapore, encrypted | Same | COS cross-region replication |
| Logs | Container stdout to **CLS** with a 30-day retention; no request bodies, no keys, no prompts (see the security spec) | Same, plus tenant id as a field for support lookups | CLS |
| Components (`anydoc` etc.) | Baked into the image (`webapp-deploy/Dockerfile`; the installer reports `anydoc` ready from the bundle). Keep it that way so `/data` can be `noexec`; the first-boot download into `/data/components` stays the desktop path | Same | none |

**Why SQLite first.** It is what the code runs today, one server serves the closed beta, and the CBS disk plus hourly COS backups give a 1-hour RPO with no new code. WAL is already on (`packages/db/src/client.ts:44`); add `busy_timeout` before more than one writer exists. CBS is a block device, so WAL is safe; never put the SQLite file on a network filesystem. Postgres becomes worth it when tenancy lands (Phase 3): concurrent writers, row-level policies, and managed PITR. Postgres is not a config switch today: `packages/db/src/vault-key.ts:23-27` throws on a `postgres://` URL, so Phase 3 includes a driver and migration change. Do not move earlier.

**Why COS for blobs before Postgres.** Media and job outputs are already keyed by org id on disk, so a per-tenant prefix on COS is a small change, and it removes the biggest disk-growth risk from the CVM. Phase 6 in the migration plan.

## 4. Sizing to start

| Item | Start | Why |
|---|---|---|
| CVM | 4 vCPU / 8 GB, standard family, Ubuntu 22.04 LTS | the image is 1.2 GB on disk; ffmpeg and SQL workers are CPU-bound bursts |
| System disk | 50 GB CBS Premium SSD | OS, Docker, images |
| Data disk | 200 GB CBS Premium SSD, mounted `/data`, `nodev`; `noexec` only after the component installer stops loading native modules from `/data/components` (security spec H3) | SQLite plus media until Phase 6 moves blobs out |
| COS | one media bucket, one backup bucket, both private | separate policies and lifecycles |
| TencentDB for PostgreSQL | not yet; order at Phase 3 | see above |
| CLB | one HTTPS listener with a certificate from SSL Certificate Service, or Caddy on the CVM as shipped in `webapp-deploy/` | Caddy is enough for one CVM; move TLS to CLB when there are two |

## 4b. Worst-case sizing (asked by Kyo, 2026-09-18)

What actually burns local CPU and RAM is small and known; everything model-shaped goes to the gateway. Per concurrent job, from the code:

| Local job | Cost per concurrent job | Cap today | Where |
|---|---|---|---|
| ffmpeg render (h264 crf 20, preset medium, project resolution) | 2-4 vCPU, 0.3-0.6 GB, up to `10 x timeline + 60 s` | `AGENTFORGE_MAX_FFMPEG` (2), queue 4x | `packages/host/src/edit/ffmpeg/run.ts:72-124`, `recipes.ts:221-262` |
| SQL worker (in-memory SQLite) | 1 vCPU burst, 128 MB heap hard limit, 2 s per query | `AGENTFORGE_MAX_SQL_WORKERS` (4) | `packages/host/src/sql-runner.ts`, `datasets.ts:110-111` |
| PDF extraction (worker thread) | 1 vCPU, 0.2-0.4 GB for a 25 MB / 500-page file, 20 s | **none** | `packages/core/src/pdf/index.ts:30-32` |
| anydoc conversion (native, libuv pool) | 1 vCPU, 0.1-0.3 GB | **none** beyond the 4-thread libuv pool | `packages/host/src/file-extract/anydoc.ts:153-168` |
| DOCX extraction | runs **on the request thread**, up to 20 s, blocks every other request meanwhile | none | `packages/host/src/knowledge-extract.ts:29-34` |
| Buffered request body | up to 26 MB RAM each, held for the request | none | `packages/host/src/http-adapter.ts:41,111` |
| Node host baseline | 0.5-1 GB with SQLite page cache and caches | | |

Worst case is set by the caps, not by the user count: raise `AGENTFORGE_MAX_FFMPEG` and you buy vCPUs for it. Assume 10 % of active users are inside a heavy job at the same moment and 10 % are mid-upload.

| Concurrent active users | Heavy jobs at once | vCPU | RAM | Tencent CVM (verify names in the console) |
|---|---|---|---|---|
| 20 (one Enterprise org) | 2 renders, 2 SQL, 2 extractions | 8 | 16 GB | S5.2XLARGE16 |
| 100 (five orgs or 100 Personal) | 10 renders, 10 SQL, 10 extractions, 10 uploads | 32 | 64 GB | S5.8XLARGE64 |
| 200 | 20 renders, 20 SQL, 20 extractions | 64 | 128 GB | S5.16XLARGE128, and this is the last size that makes sense |

Past roughly 150-200 concurrent users a bigger CVM stops helping: the host is one Node process (one event loop, and DOCX extraction blocks it) on one SQLite writer. The next step is Postgres (Phase 3 decision point) plus two app instances behind CLB with ffmpeg moved to a worker box, not a larger machine.

**Disk is the real worst case.** Nothing is cleaned up today (no retention job anywhere in `packages/host/src`); edit scratch, datasets, media and renders accumulate per project, and a 1080p render is roughly 60-90 MB per minute of video. Budget 1 TB of CBS for the media-heavy case until Phase 6 moves blobs to COS, and note that `backup.sh` tars all of `/data` hourly, which stops being workable long before 1 TB: Phase 6 or an incremental backup has to land first.

**Network.** Outbound is the gateway plus public fetches capped at 1.5 MB / 15 s each (`packages/core/src/security/safe-fetch.ts:4-6`), Research at 3 concurrent page reads. Inbound bandwidth on the CVM (Tencent bills by Mbps or by traffic) matters more than CPU for the video case: 100 users downloading renders is 100 x 10 Mbps.

**Before Phase 5 caps:** add limiters for PDF and anydoc extraction and move DOCX extraction off the request thread; those three are the uncapped paths that let one tenant take the box down (security spec T9).

Notes that change the bill more than the instance choice:

- **Bill by traffic, not by bandwidth.** 50 Mbps of fixed bandwidth is $549/month in Jakarta; the same 500 GB of downloads billed by traffic is $60. Switch to bandwidth billing only when sustained outbound exceeds about 4 TB/month.
- **The AMD families are cheaper for the same shape.** SA5.8XLARGE64 is $512 against S5.8XLARGE64 at $603 and S8.8XLARGE64 at $717. Nothing in the host is CPU-family specific.
- **Yearly prepaid is roughly 8 months of list price** (SA5.8XLARGE64: $3,932/year). Do not prepay before Phase 3 proves the shape.
- **Postgres is the second-largest line** from Phase 3 on. It is also the line that lets the app outgrow one CVM, so it is not optional past 100 users.
- **The gateway bill is not in this table.** Model, image and video usage is billed by Toko Token per tenant and is the cost the subscription and the seats must cover; it will dwarf the hosting bill at any real usage.
- **Excluded:** domain, a Tencent SSL certificate (Caddy uses Let's Encrypt), Anti-DDoS Basic (included), the Singapore backup replica (add COS cross-region traffic at $0.081/GB if turned on).
## 5. Backup and recovery targets

- **RPO:** 1 hour (hourly `backup.sh` to COS), 24 hours for the CBS snapshot.
- **RTO:** 2 hours: new CVM from the image, attach or restore the data disk, `restore.sh` from the latest COS object, point DNS.
- **Drill:** restore into a scratch CVM once a month; record the result in `webapp-deploy/DEPLOY-LOG.md`.
- **Tenant deletion:** a tenant's rows, its COS prefix, and its envelope must be deletable on request within 30 days; backups age out on the lifecycle above. This is a UU PDP obligation and a Phase 3 acceptance test.

## 6. What this does not decide

1. Tenant column vs schema-per-tenant in Postgres (migration plan, open question).
2. Whether the operator gateway key for Personal lives in the same envelope as BYO keys (decision 8).
3. A second CVM behind CLB for availability. Not before paying tenants exist.
