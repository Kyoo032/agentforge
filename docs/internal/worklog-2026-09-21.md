### 2.1 Meeting: the transcription pipeline actually runs

**Why.** The mode was dead end to end. Every recording failed at the `extracting` phase with
"ffmpeg recipe failed", so neither the minutes leg nor the translation leg had ever executed.

**Root cause, and it was arithmetic, not the gateway.** `timeoutForMedia`
(`packages/host/src/edit/ffmpeg/recipes.ts:41-43`) turned a probed duration into milliseconds:
`2 * 65.556063 * 1000 + 30_000` is `161112.126`. `child_process.execFile` refuses a non-integer
`timeout` with `ERR_OUT_OF_RANGE` **before it spawns anything**, and the catch-all in
`packages/host/src/edit/ffmpeg/run.ts` reported that as `ffmpeg_failed`. So every recording whose
audio was not a whole number of seconds long — every real recording — blamed ffmpeg for a request
ffmpeg never received. `runFfmpeg` now rounds the budget up once, for every caller, and the failure
message carries the exit code and the tail of stderr. Edit's probe, extract and render recipes were
broken the same way and are fixed by the same change.

**Second root cause.** The model the picker chose cannot transcribe on this gateway.
`mimo-v2.5-asr` is not in the live catalog (139 ids, 2026-09-21), so `pickTranscriptionModel` fell
through to `qwen3-livetranslate-flash`, which answers `503 get_channel_failed`. `gpt-audio` answers
`200` with a refusal sentence. Even with ffmpeg fixed, transcription could not have succeeded.

**What works, one short chunk each, against the live gateway:** `gemini-3.5-flash` (verbatim, and the
only id that labels speakers), `gpt-audio-mini` (fastest), `gpt-audio-1.5` (verbatim when streaming),
`qwen3-omni-flash-2025-12-01` (only with a data URI). `TRANSCRIPTION_PREF` is now that order.

**The request shape is per model family, and each variant cost a live 400 to learn.** The OpenAI audio
family takes bare base64 in `input_audio.data` and answers `400 invalid_value` to a data URI; the
DashScope-backed qwen/omni family takes a `data:` URI, answers `400 InvalidParameter` to bare base64,
and wants `stream: true`. `transcriptionShapeFor` returns wire + encoding + stream;
`packages/host/src/meeting/transcribe-request.ts` builds the call and accumulates SSE deltas.

**One dead model no longer kills a run.** Transcription walks a chain: a model that refuses, times out
or answers with nothing is dropped and the next is asked, and the first that answers is preferred for
every remaining chunk. A `200` with no text counts as a refusal, which is how `gpt-audio`-style soft
refusals are caught. A pinned `AGENTFORGE_MEETING_ASR_MODEL` still means exactly one model.

**Three PR #66 review findings closed in the same pass.** `isTranscriptionModelId` refuses every
`*-realtime` id, TTS ids, and anything whose `mediaKind` is image, video or other, so the `usable[0]`
fallback that could hand a meeting to a video model is gone (finding 2); the omni family sends
`stream: true` (finding 3); a caller's abort signal is now *composed* with the 300 s per-request
budget instead of replacing it (finding 7).

### 2.2 Meeting: record in the browser

**Why.** The studio only accepted a file. A meeting you are in the middle of is not a file.

**What it is.** A Record control beside the existing file input on `/meeting`, with a source toggle
(microphone, or microphone + tab audio), a live timer and running size, pause/resume and stop. Nothing
downstream changed: the finished blob becomes a `File` named `recording-<iso>.webm` and goes through
the **same** `POST /api/v1/meetings/:id/recording` the file input uses, so the caps, the tenancy
scoping, the transcribe/minutes run and the Knowledge card are untouched.

**Audio only, by construction.** `getDisplayMedia` must be asked for video to offer a tab picker at
all, so the video track is stopped the instant the stream arrives and is never recorded; the shared
tab's audio is summed with the microphone through an `AudioContext` `MediaStreamDestination`, which is
what puts an online meeting's *remote* voices in the recording.

**It cannot produce a 413.** Recording is opus at 24 kbps — about 10.8 MB an hour — and the running
byte count auto-stops 512 KB short of the host's 25 MB cap, keeping everything captured up to that
point and saying so. `RECORDING_MAX_BYTES` in `apps/web/lib/meeting-recorder.ts` is a deliberate
duplicate of `MEETING_RECORDING_MAX_BYTES` in `packages/host/src/meeting/store-files.ts`: the renderer
must not import `@agentforge/host`, and `@agentforge/core` exports no meeting file limit. A test pins
the number so the two cannot drift silently.

**Found by driving, not by the tests.** The first build disposed the recorder controller on unmount
with a terminal flag. Under `<StrictMode>` React mounts, runs the unmount cleanup and mounts again
against the *same* controller, so Record was silently inert — pressed, and nothing happened, no error,
no state change. All 36 unit tests passed. The controller now uses a generation token: `dispose()` is
an ordinary boundary that orphans in-flight steps and releases hardware, never a death.

### 2.3 Music: the gateway's relay model reaches the picker

**Why.** `/music` showed a greyed-out model dropdown with nothing in it, which reads as "the app does
not see my gateway's music model". `GET /api/v1/music` answered `{"items":[],"models":[],"defaultModel":"suno_music","ready":true}`
and `GET /api/v1/models` answered `modes.music: []` on a desk whose key works and whose catalog has
148 ids.

**Root cause: the Music list was built by filtering the live catalog, and a relay model is never in
it.** `GET /v1/models` on a new-api / one-api gateway lists the OpenAI-shaped models only. `suno_music`
is a *task* model driven through its own mount on the gateway origin (`POST /suno/submit/music`,
`GET /suno/fetch/<id>`) and billed per call, so it does not appear there even for a key that can use
it. `listMusicModels` and `modeCatalogPayload` filtered the catalog with `isMusicModelId`, so the list
could never contain the one id the whole mode runs on — while `defaultModel` resolved to `suno_music`
anyway through the fallback. A list that cannot contain its own default is the dead picker.

**Generation itself was never blocked.** `musicGenerateBodySchema` takes any non-empty `model` string
and nothing between the route and the relay checks the id against the live catalog. The fix is the
list and the picker, not the job path, and no new rejection was introduced.

**Fix.** New named constant `RELAY_ONLY_MUSIC_MODEL_IDS` in `packages/core/src/models/media-kind.ts`
(today just `suno_music`), merged into the catalog music ids by `withRelayMusicModels` in
`packages/host/src/selectable-models.ts`: immutable, deduped case-insensitively, and the catalog's own
row always wins a collision so its price and curation survive. `handleGetMusic` resolves the default
first and merges it in too, so an agent or Settings pin naming a relay id this build does not know is
still shown. The constant is fixed in the repo — never read from a request, a response or settings.

**UI.** An empty model list now renders `music-studio-no-models` — a titled explanation in both locales
with Submit and Draft-lyrics disabled — instead of a silently disabled select. Gateway errors from
generation now reach the banner whichever shape they arrive in: `readApiErrorMessage`
(`apps/web/lib/music-models.ts`) reads both the enveloped `{error:{code,message}}` of an `ApiError` and
the flat `{error:"gateway_blocked",status,message}` of a gated route. Before this, a 403 from the gate
came out as the generic "Music generation failed".

**No network probe was added.** A cheap relay-existence check is possible but would be a call on the
request path for a decision a constant already answers.

### 2.5 Host: auth start, state binding, client auth, plans route

**Why.** The four auth routes existed and nothing called them, the login handler read only `code` with
no CSRF binding, and there was no way for a renderer to ask what the plans are.

**What landed.**

- `GET /api/v1/auth/start` mints a login `state`, sets it as `__Host-agentforge_login_state`
  (HttpOnly, SameSite=Lax, 10 min) and returns the portal's `authorizeUrl`. Hosted only: a 404 off
  server mode, the same shape the billing webhook uses.
- `POST /api/v1/auth/login` now reads `state` from the body and compares it with that cookie through
  `statesMatch`, and clears the cookie on **every** answer — so a state is spent whether the sign-in
  worked, was refused, or was forged. A missing, stale or forged state is `invalid_request` in all
  three cases.
- The code exchange is a **confidential** client: `AGENTFORGE_PORTAL_CLIENT_ID` /
  `_CLIENT_SECRET` are sent by the host process, never by the browser, and there is no unauthenticated
  fallback.
- `GET /api/v1/billing/plans` → `{ currency, tiers, current }`, session-gated, not behind the gateway
  gate. `GET /api/v1/billing/plan` gained `tierId`. `POST /api/v1/billing/top-up` answers
  `available: false` with `billing_provider_not_configured` unless `AGENTFORGE_BILLING_TOPUP_URL` is
  set.

### 2.6 `apps/portal`: a real portal, on real Postgres

**Why.** Ruling 3 and ruling 5.1: a real login to build and review against before the backend team's
service exists, wire-compatible with `docs/internal/portal/**`.

**The three rules that make it safe to keep in the repo** (`apps/portal/AGENTS.md`): the portal never
imports the product (no `@agentforge/db`, no `@agentforge/host`, not even `@agentforge/core`); the
product never imports the portal; and `docs/internal/portal/migrations/0001-0005` are the backend
team's files, read at runtime and never edited.

**Store.** Postgres only. `PORTAL_DATABASE_URL` is required, must be `postgres://`, and is never
`DATABASE_URL`. `store.tx(tenantId, ops => …)` is the only way to reach a row, because every RLS
policy in `0004_rls.sql` reads `app.tenant_id` and `SET LOCAL` only exists inside a transaction.
`tx(null, …)` is the pre-authentication window and reaches exactly the two tables whose policies
expose it. `store.resolve.*` are the `SECURITY DEFINER` resolvers and each returns at most a tenant
id, so none of them tells a caller whether a value was ever valid.

**New migrations, `0006-0008`.** `0006_browser_login.sql` adds `oauth_clients`, `auth_codes`,
`device_codes.platform` and the poll-window counters. `0007_tenant_resolvers.sql` adds the
`SECURITY DEFINER` tenant resolvers that `schema.md` and `device-code-login.md` both flag as missing
from 0005. `0008_oauth_client_scope.sql` closes the pre-authentication window 0006 opened on
`oauth_clients`, which nothing needed.

**Endpoints.** The browser flow (`/authorize` and its two form posts), the device-code flow
(`/auth/device/code`, `/activate`, `/auth/device/approve`, `/auth/device/token`), `/auth/token` for
both grants, `/auth/logout`, `/auth/session`, `/tenant/config`, `/.well-known/jwks.json`, `/healthz`.

**Security, as built.** No password ever. OTP is 6 digits / 10 min / 5 attempts / single use / 3 sends
per 15 min per address, enumeration-resistant (an unknown or ambiguous address renders the same page
and sends nothing, and the code is minted before the lookup so the work is the same on every path).
Raw codes and tokens are never stored — only `sha256(raw)` in a `bytea` with a length CHECK. Secret
comparisons use `hashEquals`. `src/log.ts` drops credential-named fields and scrubs token-shaped
values at the sink. Every page interpolation goes through the `html` tag; `raw()` is the only escape
hatch and exists to be greppable. One `Set-Cookie` per response, because `PortalResponse.headers` is a
`Record<string, string>` and a second cookie has nowhere to go.

**Mail.** Real SMTP to Mailpit locally; `loadConfig` refuses to start a production process with no
`PORTAL_SMTP_HOST`. `pnpm portal:otp <email>` **issues** a code (it cannot read a stored one back),
needs `PORTAL_ALLOW_MANUAL_OTP=1`, is refused in production, and writes `otp.issued_manually`.

**Files.** `apps/portal/` in full — 100 untracked paths, including `AGENTS.md`, `README.md`,

### 2.7 Renderer: sign-in, callback, session provider, boot order

**Why.** SR-06: a signed-out hosted visitor landed on the **paste-your-key onboarding screen**. The
first screen of the public deployment asked a stranger for a gateway API key.

**The boot order is now ping → session → settings.** `SessionProvider` wraps the app;
`bootView(status)` collapses the session state into `loading | sign-in | app`. The `/api/v1/settings`
fetch is skipped entirely unless `view === "app"`, because in server mode that call answers
`401 session_required` for a visitor with no session and the old `.catch` read that as "onboarding".
Off a hosted deployment `view` is `"app"` as soon as ping answers, so webdev and the desktop reach
settings exactly as they always did.

**Three routes are public**, checked as a set rather than routed through a nested `<Routes>` (a
descendant route table under `path="*"` matches on the *remaining* path and would silently stop
matching these absolute paths): `/sign-in`, `/auth/callback`, `/pricing`.

**A hosted visitor with no session sees the sign-in screen in place**, wherever they aimed, rather
than being redirected — so a session that ends mid-use does not rewrite the address bar under the
person.

**The full page reload after sign-in is load-bearing**, not cosmetic: it issues a GET, which is the
only thing that re-mints the session-bound CSRF cookie (SR-07).

**One hosted-only shell fix came out of this.** `apps/web/vite.config.ts` sets `base: "./"` for the
packaged desktop, and the hosted server answers every non-`/api/` GET with that same shell — so at
`/auth/callback` the shell's own `./assets/index-<hash>.js` resolves to `/auth/assets/…`, which is not
a file, so the SPA fallback answers it with the shell again as `text/html` and the browser refuses the
module. `rootRelativeAssets` (`apps/web/lib/hosted-build.ts`) rewrites those to root-relative, hosted
only. Without it the hosted deployment cannot be signed in to at all. `/pricing` and `/sign-in` survive
only because they happen to be one segment deep.

### 2.10 Portal CSP `form-action`, and the product name in the mail

**Why.** The six-digit code page did nothing when the button was pressed, in a real browser, silently.

**Root cause.** `apps/portal/src/security/headers.ts` sent one frozen policy on every HTML answer,
`form-action 'self'` included. A browser applies `form-action` to **every hop of a submission's
redirect chain**, and `POST /authorize/verify` ends its successful path on a `302` to the client's
`redirect_uri` — another origin. Chromium refused the post before it left the page. Nothing in the
suite saw it: every existing drive is `fetch`/curl, and **a non-browser client does not implement CSP
at all**.

**Fix.** The policy is built per response. `formActionSource` reduces a URL to exactly
`new URL(x).origin` and answers `null` for anything that is not an http(s) origin. `URL.origin` hands
back `https://a;b` and `https://a,b` unchanged — in a CSP header a `;` starts a directive and a `,`
splits the header into two policies — so the origin is matched against a narrow host charset rather
than trusted because `URL` parsed it. `routes/authorize.ts` is the only caller, and each of its three
call sites runs **after** `checkClient` has exact-matched that `redirect_uri` against the client's
registered allowlist. Every other page stays at `'self'`.

**The lesson, which is bigger than the bug:** a header only a browser enforces cannot be verified by a
client that does not enforce it. CSP, `__Host-` cookie acceptance, `SameSite` and mixed-content
blocking are all in that class.

**Mail product name.** The sign-in mail carried a constant of its own ("Toko Token AI") while every
page of the same sign-in said DPSBuddy. `apps/portal/src/otp/product-name.ts` now resolves one
order: `tenant_config.branding.product_name` → `tenants.name` → the portal's own `product` locale key.
A value that differs from the tenant slug only by case, spaces, hyphens or underscores is treated as
absent, because the seed defaults `--tenant-name` to the slug — so "the operator chose a display name"
and "the operator chose nothing" would otherwise be the same row, and a bare slug like `dpsbuddy`
would appear in a subject line under a page saying DPSBuddy.

**Register:** SR-20, fixed and driven in Chromium.

### 2.11 Review harness: `review-proxy.mjs` and `review-instance.ps1`

**Why.** Hosted mode cannot be reviewed over plain http. `rejectPlaintext` answers
`403 https_required` without `X-Forwarded-Proto: https`, and `trustedOrigins` drops every `http://`
entry in server mode. So the review instance is four things on loopback, and one command that starts
them.

**What it is.** `scripts/review-proxy.mjs` terminates TLS on 3443 with a self-signed pair it generates
under `$HOME/.dpsbuddy-review/tls`, stamps `X-Forwarded-Proto: https`, appends `X-Forwarded-For` and
passes `Host` unchanged. `scripts/review-instance.ps1` starts Docker compose (Postgres + Mailpit), the
portal on 4000, the app on 3100 in server mode with its **own** data dir, and the proxy on 3443.

**What the script will not do**, stated in its own header and verified: it never touches `:3000` or
`.webdev-data`; it refuses a data dir that resolves inside the checkout or is named `.webdev-data`; it
never starts Docker Desktop; it never writes a secret into the repository; and `-Stop` kills only the
three process ids **this** script recorded, and only when the running process still has the start time
recorded with the id — never by port, never by image name.

**Default is print, not run.** Without `-Start` it prints exactly what it would launch and exits 0.

**Two topologies, one command.** With no URL arguments everything is loopback. With `-AppPublicUrl` /
`-PortalPublicUrl` the four variables that must agree with the public names —
`AGENTFORGE_TRUSTED_ORIGINS`, `AGENTFORGE_PUBLIC_URL`, `AGENTFORGE_PORTAL_URL`, `PORTAL_PUBLIC_URL` —
are derived there rather than edited by hand in four places, and `PORTAL_TRUST_PROXY` switches on
exactly when there really is a proxy in front.

app and the portal so the owner could review from a phone. `cloudflared` was installed on this desk
with winget. Mailpit was never exposed. Both URLs are ephemeral and **must be closed after the
review** — recorded as **SR-28**.

## 3. How it is structured

### 3.1 The Phase 9 architecture

Three processes, and the product talks to the portal only over HTTP.

The **browser** holds no token of any kind. It holds two cookies the host sets — the session cookie and
the session-bound CSRF cookie — and, for ten minutes during a sign-in, the `__Host-agentforge_login_state`
cookie. It never sees an access token, a refresh token or a client secret.

The **app host** (`apps/web/server.ts` + `packages/host`) is the only thing that talks to the portal.
It exchanges the authorization code server-side with `client_id` + `client_secret`, keeps the access
and refresh tokens in a **process-memory vault** (SR-08: nothing at rest, at the cost of a restart
signing everyone out), and answers `GET /api/v1/auth/session` with ids, e-mail, org, seats, device
label and expiry — never a token.

The **portal** (`apps/portal`) owns tenants, orgs, users, devices, sessions and seats, in Postgres with
row-level security. It mints the six-digit code, sends it over SMTP, and hands back an authorization
code on a `302` to a `redirect_uri` it exact-matched against the client's allowlist.

```
                         ┌──────────────────────────────────────────┐
   browser               │  cookies: __Host-agentforge_session,     │
   (no tokens, ever)     │  __Host-agentforge_csrf, …_login_state   │
                         └──────────────────────────────────────────┘
        │  1. GET /api/v1/auth/start        ┌─────────────────────────────┐
        ├──────────────────────────────────>│                             │
        │     { authorizeUrl } + state ck   │        APP HOST             │
        │<──────────────────────────────────┤  apps/web/server.ts         │
        │                                   │  + packages/host            │
        │  2. top-level nav                 │                             │
        │     GET {portal}/authorize        │  memory token vault (SR-08) │
        ├───────────────────┐               │  SQLite: product data       │
        │                   │               └──────────┬──────────────────┘
        │                   v                          │  3. POST {portal}/auth/token
        │        ┌──────────────────────┐              │     client_id + client_secret
        │        │       PORTAL         │<─────────────┘     (server to server, 5 s)
        │        │  apps/portal         │
        │        │  OTP → 302 code&state│              ┌──────────────────────────────┐
        │        └──────────┬───────────┘              │  SQLite  data/agentforge.*   │
        │                   │                          │  product rows, per tenant    │
        │  302 {redirect}?code&state                   └──────────────────────────────┘
        │<──────────────────┘
        │                          ┌────────────────────────────────────┐
        │  4. /auth/callback       │  Postgres 16  (portal control      │
        │     POST /api/v1/auth/   │  plane, RLS on app.tenant_id)      │
        │     login {code,state}   │  + Mailpit (SMTP sandbox)          │
        v                          └────────────────────────────────────┘
   full page reload  →  CSRF re-minted on the GET  →  /chat signed in
```

**Which package may import which.**

| Package | May import | Must never import |
|---|---|---|
| `apps/portal` | its own `src/**` and npm | `@agentforge/core`, `@agentforge/db`, `@agentforge/host`, anything in `apps/web` |
| `apps/web` (renderer) | `@agentforge/core` subpaths, `@/lib/*` | `@agentforge/host`, `@agentforge/db`, `electron`, `@agentforge/portal` |
| `packages/host` | `@agentforge/core`, `@agentforge/db` | `@agentforge/portal`, anything in `apps/web` |
| `packages/core` | nothing in this repo above it | `@agentforge/db`, `@agentforge/host`, `@agentforge/portal` |

Two consequences worth stating because they look like duplication and are not.
`RECORDING_MAX_BYTES` in the renderer duplicates `MEETING_RECORDING_MAX_BYTES` in the host, with a test
pinning the number, because the renderer may not import the host and core exports no meeting file
limit. `HOST_AUTH_REASONS` in `apps/portal/src/flows/reasons.ts` duplicates `AUTH_REASONS` in
`packages/host/src/auth/session.ts` for the same reason, and `tokenErrorBody` enforces it rather than
trusting a call site.

The one place `apps/web` may read `window.agentforge` is still `apps/web/lib/desktop-bridge.ts`;
everything else goes through `@/lib/api-client`.

## 4. The review instance

**Launch.** From the repo root, in PowerShell. Default is print-only — read it before anything binds a
port.

```powershell
powershell -NoProfile -File scripts\review-instance.ps1              # print what it would do, exit 0
powershell -NoProfile -File scripts\review-instance.ps1 -Start -Production
powershell -NoProfile -File scripts\review-instance.ps1 -Stop
```

`-Start` is also the relaunch: anything this script started earlier and is still running is stopped

does — `NODE_ENV=production`, the built bundle from `apps/web/dist` rather than Vite — which is the
only way the production CSP, the built shell, the hosted marker and the boot refusals are exercised.

`-PortalPublicUrl`, `-PortalPort` (4000), `-AppPort` (3100), `-ProxyPort` (3443), `-ReviewRoot`
(`$HOME\.dpsbuddy-review`), `-SeedEmail` (`admindps@privaro.me`), `-SeedTenant` (`dpsbuddy`),
`-SeedOrg` (`Kyo`), `-SeedSeatCap` (2), `-PostgresService`, `-PostgresPort` (5433), `-PostgresUser`,
`-PostgresDb`, `-PostgresWaitSeconds`, `-PnpmCommand`.

Paste the printed client id and secret into `$HOME\.dpsbuddy-review\review.env`. A re-seed with a new
`--redirect` **adds** it to the client and leaves the secret alone, so a tunnel URL can be registered
without re-pasting `AGENTFORGE_PORTAL_CLIENT_SECRET`.

**Getting a login code.** Two ways, both real:

1. **Mailpit**, `http://127.0.0.1:8025` — every OTP the portal sends lands there.
2. **By hand**, when somebody needs reading out:
   `PORTAL_ALLOW_MANUAL_OTP=1 pnpm --filter @agentforge/portal otp -- <email>`. It **issues** a fresh
   code (it cannot read a stored one back — only the sha256 exists), prints it once, and writes
   `otp.issued_manually` to the audit log. Refused in production.

Root aliases `pnpm portal:dev`, `pnpm portal:seed` and `pnpm portal:otp` now exist and are the same
scripts under shorter names. (The register's SR-10 said they did not; that was true when it was
written and is **corrected** in §3 below.)

**Tunnels are ephemeral.** The two `trycloudflare.com` hostnames published on 2026-09-21 are quick

**The shape of the session fix (8), because it is the one with a design decision in it.** The portal
cookie stays a signed value rather than becoming a row; what makes it revocable is a per-user version
counter, `web_session_versions` (migration 0009, plain tenant-scoped RLS). The cookie carries the
version it was minted under; every use compares it inside the tenant scope. **No row means version
1**, so nothing had to be back-filled and a user who has never been revoked costs one indexed read
and no write. A row-per-session table would have bought per-browser revocation, which nothing needs
yet, at the price of inserts on every sign-in and a pruning job. What ends a session: `/logout`
clears this browser's cookie; `POST /auth/logout` with `all_devices: true` bumps the counter and ends
every browser that user holds. Both write `web_session.revoked` with the blast radius in
`after.scope`.

`GET /logout` and `POST /logout` clear the cookie on **every** answer, including their refusals, and
follow `post_logout_redirect_uri` only when its origin exactly matches the origin of one of that
client's registered `redirect_uris` — otherwise a neutral "signed out" page. A cookie minted before
`ver` existed is refused rather than assumed to be version 1, so everyone signed in at deploy time
signs in once more.

**One thing found while driving, not fixed here because the file belongs to another lane.**
`scripts/review-instance.ps1`'s `-Stop` cannot work on Windows PowerShell 5.1. `ConvertFrom-Json`
there returns a JSON array as a single `Object[]`, so `@($parsed)` in `Read-ReviewPids` is an array
of **one array**; `foreach ($entry in $entries)` then binds `$entry` to the whole array and
`[int]$entry.pid` throws `Cannot convert the "System.Object[]" value … to type "System.Int32"`
before anything is stopped. Reproduced exactly while writing this pass's own restart helper. The fix
is one `| ForEach-Object { $_ }` in the pipeline that reads the file (the same one is needed in
`Write-ReviewPids`'s caller). `-Start` is unaffected until it tries to stop what it started.
